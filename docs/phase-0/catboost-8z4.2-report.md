Without `override`, the object built as `probepkg.so` and the package failed to load (`shared object 'libprobe.so' not found`). This was the first of the two allowed build attempts; the fix was applied on the second.

## Step 2 — generated `src/cpp11.cpp` (verbatim)

```cpp
// Generated by cpp11: do not edit by hand
// clang-format off


#include "cpp11/declarations.hpp"
#include <R_ext/Visibility.h>

// cpp11probe.cpp
int cpp11_scalar();
extern "C" SEXP _probepkg_cpp11_scalar() {
  BEGIN_CPP11
    return cpp11::as_sexp(cpp11_scalar());
  END_CPP11
}

extern "C" {
static const R_CallMethodDef CallEntries[] = {
    {"_probepkg_cpp11_scalar", (DL_FUNC) &_probepkg_cpp11_scalar, 0},
    {NULL, NULL, 0}
};
}

extern "C" attribute_visible void R_init_probepkg(DllInfo* dll){
  R_registerRoutines(dll, NULL, CallEntries, NULL, NULL);
  R_useDynamicSymbols(dll, FALSE);
  R_forceSymbols(dll, TRUE);
}
```

Key facts read directly from this file:
- `CallEntries[]` is `static` (file-scope, not linkable from `init.c`).
- The individual wrapper (`_probepkg_cpp11_scalar`) IS `extern "C"` and externally linkable.
- The generated init function is named `R_init_probepkg` — derived from the DESCRIPTION `Package:` field, **not** from the `useDynLib`/`.so` name (`libprobe`). Since the built shared object is `libprobe.so`, R's `dyn.load()` only auto-invokes `R_init_libprobe` on load. `R_init_probepkg` is therefore dead code unless invoked explicitly — this is the exact mismatch the brief flagged as needing to be tested, confirmed by direct inspection.

## Step 3 — merge attempts

**Attempt 1 (FAILED):** hand-written `R_init_libprobe` calling `R_registerRoutines(dll, NULL, RawCallEntries, NULL, NULL)` for the raw function, then calling the generated `R_init_probepkg(dll)` (forward-declared `extern`) to register cpp11's routines, then `R_useDynamicSymbols(dll, FALSE)`.

Build succeeded with no compiler warnings. Package loaded. But calling the raw function failed:
```
Error in .Call("RawScalar_R", PACKAGE = "libprobe") :
  "RawScalar_R" not available for .Call() for package "libprobe"
Calls: raw_probe
Execution halted
```
Diagnosis via `getDLLRegisteredRoutines("libprobe")$.Call` showed only `_probepkg_cpp11_scalar` registered — `RawScalar_R` was gone. Root cause: `R_registerRoutines()` **replaces** a DLL's routine table on each call; it does not merge across repeated calls on the same `DllInfo*`. Two sequential registration calls on one `dll` handle mean only the entries from the *last* call survive.

**Attempt 2 (SUCCEEDED, within the two-attempt limit):** abandoned calling the generated `R_init_probepkg` at all (it's dead code anyway, per Step 2 finding). Instead declared `extern SEXP _probepkg_cpp11_scalar(void);` directly in `init.c` and built one combined `R_CallMethodDef` array covering both the raw and the cpp11 entry, registered with a single `R_registerRoutines` call:

```c
extern SEXP _probepkg_cpp11_scalar(void);

static const R_CallMethodDef CombinedCallEntries[] = {
    {"RawScalar_R",             (DL_FUNC) &RawScalar_R,             0},
    {"_probepkg_cpp11_scalar",  (DL_FUNC) &_probepkg_cpp11_scalar,  0},
    {NULL, NULL, 0}
};

void R_init_libprobe(DllInfo *dll)
{
    R_registerRoutines(dll, NULL, CombinedCallEntries, NULL, NULL);
    R_useDynamicSymbols(dll, FALSE);
}
```
Build succeeded, package loaded, both functions callable and correct (see below). cpp11's own `src/cpp11.cpp` needed **zero edits** — it stays exactly as generated; only its externally-linkable per-function wrapper symbols are referenced from the hand-written `init.c`.

```r

> d$dynamicLookup
[1] FALSE
```
Both `raw_probe()` and `cpp11_scalar()` still resolved and returned correct values with dynamic lookup disabled — confirming resolution went through the registered-routines table, not symbol-table fallback, and that the merge survives the same lockdown upstream uses.
