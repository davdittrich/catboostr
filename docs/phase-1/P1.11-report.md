```

CMakeLists.linux-x86_64.txt:589:target_ragel_lexers(yutil
CMakeLists.linux-x86_64.txt:597:target_yasm_source(yutil
```

`CMakeLists.darwin-arm64.txt` has **no `target_yasm_source` call at all** —
`context_aarch64.S` compiles as a plain GNU-assembler source via the C
toolchain, never through yasm. `darwin-x86_64.txt` still needs yasm,
identically to linux-x86_64. This is a structural fact of the pinned tree
(read directly, not inferred), and it is empirically confirmed by the
successful arm64 build (§4): `ragel` IS still invoked (`target_ragel_lexers`
is unconditional across all three variants) and P1.5's acquired/built ragel
binary is what generates `parser.rl6.cpp` on darwin too; the acquired yasm
binary is present (per acquire-thirdparty.sh, unconditionally acquired as a
build tool regardless of arch) but simply never invoked by CMake on
arm64 — harmless, not a bug. **P1.5's mechanism holds on darwin-arm64. It
remains structurally necessary and unverified-on-real-hardware for
darwin-x86_64**, which this runner does not provide (see §7).

## 6. Prune set validated on darwin

This is the one thing P1.13's jobs never exercise (`configure` always
builds from full `vendor/catboost`, never the pruned copy — P1.13 report
§1). The new `darwin-prune-validation` job:

1. Acquires `vendor/catboost` + `vendor/thirdparty` fresh.
2. Runs `tools/vendor/prune.sh` (Linux-derived Tier 1/Tier 2 exclusion
   set from P1.2/P1.6) — `61 / 61` listed paths removed, `1.2G -> 297M`.
3. Builds and installs the R package tarball with
   `CATBOOSTR_VENDOR_SRC=vendor/catboost-pruned`.
4. Runs the full testthat suite against that install.

Result: install succeeded (894s wall-clock), 107/107 assertions passed,
zero failures. **The Linux-derived prune set holds on darwin-arm64** — no
directory excluded by `cmake/gate-test-tool-dirs.cmake` or `prune.sh`'s
Tier 2 list was needed by the darwin-arm64 build.

## 7. Real bugs found and fixed while standing this up

1. **`prune.sh` had no macOS fallback for `sha256sum`** — macOS ships no
   `sha256sum` binary at all (`xargs: sha256sum: No such file or
   directory`, exit 127). Fixed with the same `shasum -a 256` fallback
   `verify-build-copy.sh` already used; confirmed zero manifest change on
   Linux (`HASHER` still resolves to `sha256sum` there).
2. **`R CMD INSTALL` without `--install-tests`** ships a package whose
   `tests/` directory `test_check()` can't find via `system.file()`.
   Fixed by adding the flag.
3. **`test_check()`'s `test_dir("testthat", ...)` resolves against the
   current working directory, not the installed package** — running
   `Rscript tests/testthat.R` from the repo root (not `tests/`) fails
   with "No test files found" even with tests correctly installed.
   Reproduced and confirmed in under a minute with a throwaway dummy R
   package (isolating the exact mechanism before touching CI again) — the
   real fix was `(cd tests && Rscript testthat.R)`, matching the working
   directory `R CMD check` itself always uses for this file.
