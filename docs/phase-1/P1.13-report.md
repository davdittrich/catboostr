## 1. What was created

- `.github/workflows/ci.yml` — three jobs, on `push` and `pull_request`:
  1. `build-check`, matrix `[ubuntu-latest, macos-14]` — `R CMD build
     --no-build-vignettes .` then `R CMD check --as-cran --no-manual` on the
     resulting tarball, failing the job on any `ERROR` in `00check.log`;
     WARNINGs/NOTEs are recorded in the log but not fatal (the ticket's bar
     is "fail on ERROR", not CRAN's own stricter as-cran exit code).
  2. `integrity` — `prune(fresh acquire) == manifest` and `configure's
     build-source copy == manifest`, replacing the AMENDMENT's dropped
     tarball-vs-manifest design (the R tarball ships zero `vendor/` files
     by design, per P1.6).
  3. Both jobs run `tools/vendor/acquire.sh` / `acquire-thirdparty.sh`
     first, cached by pinned SHA/key.
- `tools/vendor/verify-build-copy.sh` — hashes `configure`'s disposable
  build-source copy against `tools/vendor/PRUNED_MANIFEST.sha256`.
- `tools/vendor/prune.sh` — one-line fix, `LC_ALL=C` pinned before the
  manifest-writing `sort` (see §2.1).
- `src/CMakeLists.txt` — one-line fix, `contrib-libs-linux-headers`
  gated behind `if(NOT APPLE)` (see §2.3).
- `tools/vendor/PRUNED_MANIFEST.sha256` — regenerated twice: once for the
  locale fix, once to drop a local contamination artifact (see §2.2).

No credentials are used anywhere in the workflow.

## 2. Real bugs the hosted runners caught (none were assumed — each is
   reproduced, fixed, and re-verified green on the next push)

### 2.1 `prune.sh`'s manifest sort was locale-dependent

First integrity-job run failed with a full-file diff between the
committed manifest and a fresh CI acquisition, despite both trees being
identical. Root cause: `find . -type f -print0 | sort -z` used the
ambient locale (`en_US.UTF-8` on the machine that generated the
committed manifest; `C`/`POSIX` on the runner), so file order differed
even though content didn't. Verified by sorting both manifests and
diffing — byte-identical. Fixed with `export LC_ALL=C` before the sort;
confirmed idempotent across two consecutive local runs.

### 2.2 Local `vendor/catboost` had a stray `__pycache__` artifact

After the locale fix, the integrity job still failed — by exactly one
entry: `build/scripts/__pycache__/process_command_files.cpython-312.pyc`.
This `.pyc` was left over on the local dev machine from an earlier
Python invocation against that build script; upstream's own
`.gitignore` hides it from `git status`, so it went unnoticed until
`prune.sh`'s raw filesystem walk picked it up. Confirmed `git -C
vendor/catboost rev-parse HEAD` still matched the pin
(`b1bd2a6d77219e82a1acfcedfccb8e6f6c1ee084`) before removing it —
tracked content was never touched. Manifest regenerated: 21887 entries,
matching the CI runner's fresh clone exactly.

### 2.3 `contrib-libs-linux-headers` linked unconditionally, broke macOS

`src/CMakeLists.txt:50` linked this library from upstream's
`CMakeLists.linux-x86_64.txt` reference file without noticing it's
platform-gated there. Confirmed by grepping
`vendor/catboost/catboost/R-package/src/CMakeLists.*.txt`: `linux-headers`
appears only in the `linux`/`linux-*-cuda` variants, never in
`darwin-arm64.txt` or `darwin-x86_64.txt`. On the macOS runner this
produced `ld: library 'contrib-libs-linux-headers' not found`, `clang:
error: linker command failed`. Fixed by wrapping the single
`target_link_libraries` call in `if(NOT APPLE) ... endif()`, matching
the pattern already used a few lines below for `target_link_options`.

### 2.4 Hosted runners have no `pdflatex`

Once linking succeeded, `R CMD check --as-cran` still failed: "checking
PDF version of manual without index ... ERROR", traced (via a
diagnosability fix, §2.5) to `pdflatex is not available`. An
environment gap, not a code defect. Fixed with `--no-manual`.

### 2.5 `00install.out` was never captured on failure

The first two macOS failures produced zero compiler diagnostics — `R
CMD check` exits non-zero on ERROR, which killed the workflow script
under `set -e` before its own log-printing lines ran, and R never
streams `00install.out` to stdout regardless. Fixed by capturing the
exit status explicitly and always printing `00install.out` +
`00check.log` before deciding pass/fail. This diagnosability fix is
what made §2.3 and §2.4 findable at all.

### 2.6 `--as-cran`'s own exit code is stricter than the ticket's bar

After §2.3's fix, macOS produced 6 WARNINGs, 4 NOTEs, zero ERROR in
`00check.log` — yet the job still failed. `R CMD check --as-cran` exits
non-zero on WARNING too (CRAN policy), which is stricter than this
ticket's stated bar ("fail the job on any ERROR ... record WARNINGs and
NOTEs in the log"). Fixed by gating on a literal `ERROR` grep against
the check log, not R's own exit code.

### 2.7 The pristine-guard's `tee | grep -q` had a pipe race

Both early macOS runs failed the "Guard -- vendor/catboost still
pristine" step with **zero** diagnostic output — `git status --porcelain
| tee /dev/stderr | (! grep -q .)` is racy: `grep -q` exits on its first
matched line and can SIGPIPE `tee` before the stderr copy flushes,
silently swallowing exactly the porcelain output needed to tell a real
dirty-tree failure from a spurious one. Fixed by capturing the
command's output into a variable first and deciding from that value,
removing the race. Once fixed, the guard passed cleanly on both
platforms — the tree was never actually dirty; every earlier "failure"
of this step was the race, not a real INVIOLABLE violation.
