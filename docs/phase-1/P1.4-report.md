## 3. Design decisions and the one real deviation

### 3a. R's CC/CXX are queried and printed, but the compiler stays clang/clang++

The ticket's MUST list says "forward `R CMD config` values: CC, CXX, CFLAGS,
CXXFLAGS, CPPFLAGS, LDFLAGS." `configure` queries all six and prints them
(Section 1 of the script). CFLAGS/CXXFLAGS/CPPFLAGS/LDFLAGS are genuinely
forwarded into the CMake build via a fork-owned toolchain file
(`CMAKE_C_FLAGS_INIT`/`CMAKE_CXX_FLAGS_INIT`/`CMAKE_EXE_LINKER_FLAGS_INIT`/
`CMAKE_SHARED_LINKER_FLAGS_INIT`) — these are project-global, so they affect
every translation unit in the build, not just the fork's own two.

CC/CXX do **not** replace clang/clang++ as the compiler. This was attempted
literally first and failed with hard evidence, not a guess:

```
$ ./configure   # with CMAKE_C_COMPILER/CMAKE_CXX_COMPILER = "gcc"/"g++" (R's real values on this machine)
[1/4265] Building C object contrib/libs/libunwind/.../Unwind-wasm.c.o
FAILED: ...
gcc: error: unrecognized command-line option '-fcolor-diagnostics'
gcc: error: unrecognized command-line option '-faligned-allocation'
gcc: error: unrecognized command-line option '-fdebug-default-version=4'
gcc: error: unrecognized command-line option '-fuse-init-array'
```

Root cause: `vendor/catboost`'s generated `CMakeLists.*.txt` bake
clang-specific per-target compile flags unconditionally, independent of any
toolchain file (`-fcolor-diagnostics`, `-faligned-allocation`,
`-fdebug-default-version=4`, `-fuse-init-array`,
`-Wimport-preprocessor-directive-pedantic`, ...). These live under the
read-only `vendor/catboost/` pin and cannot be edited. clang is not a
preference here — it is the only compiler the pinned tree's generated build
files support. Reverting the compiler binary to clang/clang++ (matching the
ticket's own "proven invocation, do not re-derive") while keeping the
CFLAGS/CXXFLAGS/CPPFLAGS/LDFLAGS forwarding is the resolution that satisfies
the most of the MUST that is actually satisfiable against this pinned tree.
**This is a partial deviation from the ticket's literal text and is flagged
as a concern below, confidence 90** (the failure is measured, not inferred;
the judgment that clang-pinning is the correct resolution given "do not
re-derive" is a documented assumption, not dictated by the ticket).

### 3b. `-fuse-ld=lld` is required, not cosmetic

Dropping `vendor/catboost/build/toolchains/clang.toolchain` in favor of a
minimal fork-owned toolchain file (to avoid re-deriving CUDA/`ENV{CC}`
settings that don't apply here) initially also dropped its
`-fuse-ld=lld`/`CMAKE_EXE_LINKER_FLAGS -fuse-ld=lld` line. Real build
evidence this was load-bearing:

```
$ ninja catboostr   # without -fuse-ld=lld (system default: GNU ld)
[1043/4265] Linking CXX executable contrib/libs/flatbuffers/flatc/flatc
/usr/bin/ld: contrib/libs/cxxsupp/libcxxrt/liblibs-cxxsupp-libcxxrt.a(exception.cc.o): in function `terminate_with_diagnostics()':
exception.cc:(.text._ZL26terminate_with_diagnosticsv+0x19a): undefined reference to `__cxa_demangle'
```

Confirmed via `nm` on the archives: `__cxa_demangle` **is** defined
(`liblibs-cxxsupp-libcxxabi-parts.a`, `T __cxa_demangle`) and **is**
referenced (`liblibs-cxxsupp-libcxxrt.a`, `U __cxa_demangle`) — but the link
line lists the defining archive *before* the referencing one, and GNU ld's
single-pass archive resolution never revisits an already-scanned archive.
Isolated repro (identical link command, only the linker driver flag
changed):

```
$ clang++ ... [same objects/archives, no -fuse-ld=lld] -o /tmp/flatc_noflags
/usr/bin/ld: ... undefined reference to `__cxa_demangle'   # fails, no output produced

$ clang++ -fuse-ld=lld ... [identical objects/archives] -o /tmp/flatc_lld
$ ls -la /tmp/flatc_lld
-rwxr-xr-x 1 dd dd 9065584 Jul 31 11:02 /tmp/flatc_lld   # links clean
```

`lld` tolerates the archive order that GNU `ld` does not. `-fuse-ld=lld` was
restored to the toolchain file (matching `clang.toolchain`, per "do not
re-derive"), applied unconditionally on non-Apple. Confidence 95 (isolated
before/after repro on the exact failing command).

## Concerns for the caller

1. **CC/CXX are not literally substitutable** (Section 3a). `configure`
   queries and prints R's CC/CXX but the actual compiler stays clang/clang++
   because `vendor/catboost`'s generated `CMakeLists.*.txt` hardcode
   clang-only flags project-wide and cannot be edited (read-only pin). If a
   CRAN build machine's R is configured with a compiler that isn't
   clang-compatible in some other way, this configure would still compile
   with clang regardless — flagging for the ticket owner to confirm this
   reading of "forward CC/CXX" is acceptable, or to open a follow-up ticket
   if literal substitution is a hard requirement (which would need
   `vendor/catboost`'s generated CMakeLists to stop hardcoding clang-only
   flags, i.e. a change to the pinned tree's generation process upstream of
   this repo, not something `configure` alone can fix).
2. **macOS path is implemented but unverified.** `configure`'s Darwin branch
   (`.dylib` detection, non-`-fuse-ld=lld` linker flags) mirrors upstream's
   own `OS_TYPE` pattern but was never run — this ticket's agent has Linux
   only. Flagged per the ticket's own admission ("Linux is the only OS this
   was actually run on").
3. **`R/install.R:catboost_download_dynlib()` still exists as dead code**
   (Section 7) — out of this ticket's `configure`-only scope, needs its own
   ticket if full source removal is required.
4. **`-j4` is `configure`'s parallelism default** (`CATBOOSTR_JOBS`,
   overridable); this session used `CATBOOSTR_JOBS=16` for both timed runs
   to stay within the sandbox's ~12 GB free RAM at build time (32 cores
