## 0. One-paragraph result

Conan is gone from the install path. `R CMD INSTALL` now builds openssl,
ragel and yasm from tarballs that are pinned to an exact version and verified
by SHA256 twice — once at acquisition, once again on every build — and

build was demonstrated to succeed with an **empty Conan cache**, an

records and refuses any invocation** — the tripwire log is empty, so Conan was
not merely offline, it was never called. `conan.lock` is generated, committed,
and used with `--lockfile` by the one remaining maintainer-side tool.
`git -C vendor/catboost status --porcelain` is empty.

## 2. Can zlib come from R? (Section IV step 2) — the question is moot

Measured, in order:

1. **CatBoost does not ask for zlib.** `find_package(ZLIB` over every
   `CMakeLists*.txt` and `cmake/*.cmake` in the pinned tree: **zero hits**.
   CatBoost carries `contrib/libs/zlib` and compiles it in-tree; the only
   other `ZLIB` occurrences are `-DHAVE_ZLIB` compile definitions on
   `contrib/libs/protobuf` and `contrib/libs/protoc`, which refer to that
   in-tree copy.
2. **zlib was purely a Conan artefact.** It entered the graph only as a
   transitive requirement of the Conan `openssl` recipe (and of several
   autotools tool recipes) — see `docs/phase-0/catboost-8z4.1-report.md`
   §1, which lists `zlib 1.3.2` in the 13-package closure and notes it is
   "shared transitive dep [of] both `openssl` requirement [and]
   `tool_requires`". This ticket's own `conan.lock` reproduces that:
   `"requires": ["zlib/1.3.2#...", "openssl/3.0.15#..."]`.
3. Configuring openssl with `no-zlib` (§3.2) removes that edge. **After this
   ticket, zlib appears nowhere in the dependency graph.**
4. **R does expose a zlib, had it been needed.** `$(R_HOME)/etc/Makeconf`
   contains

   ```
   LIBS =  -lpcre2-8 -ldeflate -lzstd -llzma -lbz2 -lz -ltirpc -lrt -ldl -lm -licuuc -licui18n
   ```

   i.e. `-lz` is on R's own link line and would be reachable. (`R CMD config
   LIBS` itself errors with `no information for variable 'LIBS'`; the value
   has to be read from `Makeconf`, which `R CMD config` sources.)

**Answer: `zlib_from_r: false` — but because zlib is not vendored and not
needed at all, not because R's copy was rejected.** Reporting it as `true`
would imply this build links R's `-lz`, which it does not.

**Confidence: 95.**

## 3. How ragel, yasm and openssl are supplied offline (Section IV steps 3-4)

### 3.1 The choice, and its consequence for the user

Two options were genuinely on the table for the two code generators:

| | vendored source, built by `configure` | `SystemRequirements:` external tool |
| :--- | :--- | :--- |
| offline with empty cache | yes, unconditionally | yes, *if* the user has them |
| availability | always | **ragel 6.10 is absent from current mainstream distro repositories**; yasm is present but not in a base build image |
| integrity | SHA256-pinned by us | whatever the distro shipped, unpinned |
| cost | **measured: ragel ~5 s, yasm ~2 s** | zero |
| failure mode | none observed | install aborts on most machines |

**Chosen: vendored, pinned source, built during `configure`.** Trading ~7
seconds of build time for an install that works on a machine with nothing
pre-installed is not a close call. The same mechanism was extended to openssl
(**measured: ~10 s** to build static+PIC at `-j16`), which additionally gets
us an exact-version pin on a *linked* library.

**Consequence for the user**, stated plainly:

* The install needs `perl` (openssl's `Configure` is a Perl program), a C and
  C++ compiler, and `make`, in addition to the `cmake` + `clang` + `python3` +
  `cython` this package already required. `perl` is the only genuinely new
  requirement.
* Install time grows by ~17 s (all three tools) on a 32-core machine. Against
  a ~176 s full CatBoost build, that is under 10%.
* The user needs **no network at install time** and **no Conan at all**.
* The user carries a statically-linked openssl, i.e. they do not get their
  distribution's openssl security updates. That is the price of the pin, and
  it is why `SOURCES.md` carries a standing CVE-tracking obligation rather
  than a footnote.

### 3.2 What was implemented

`tools/vendor/acquire.sh` and `tools/oracle/cli/acquire.sh`: a `name|version|sha256|url`
table, download to a `.part` file, verify, and only then `mv` into place. A
mismatch deletes the download and exits non-zero. An **already-present file
with a wrong checksum is a hard error, never silently overwritten**.

| yasm | 1.3.0 | `3dce6601b495f5b3d45b59f7d2492a340ee7e84b5beca17e48f862502bd5603f` | recomputed on download |

**`configure` §3b** (new section) — re-verifies all three SHA256s on **every**
build via `catboostr_verify_tarball()`, before a single byte is extracted:

```sh
catboostr_verify_tarball() {
  _tb="${THIRDPARTY_SRC}/${1}-${2}.tar.gz"
  if [ ! -f "$_tb" ]; then ... exit 1; fi
  _actual=$(catboostr_sha256 "$_tb")
  if [ "$_actual" != "$3" ]; then
    echo "*** SHA256 MISMATCH for $1 $2 -- refusing to build." >&2
    ...
    exit 1
  fi
}
```

This is the fail-closed gate: an acquisition-time-only check would not survive
a later tamper of `vendor/thirdparty/`. Observed on the real build:

```
*** verified openssl 3.5.7 sha256=a8c0d28a529ca480f9f36cf5792e2cd21984552a3c8e4aa11a24aa31aeac98e8
*** verified ragel 6.10 sha256=5f156edb65d20b856d638dd9ee2dfb43285914d9aa2b6ec779dac0270cd56c3f
*** verified yasm 1.3.0 sha256=3dce6601b495f5b3d45b59f7d2492a340ee7e84b5beca17e48f862502bd5603f
```

Build recipes, and why each non-default flag is there (all three were derived
from real failures, none are cargo-culted):

* **openssl**: `./config no-shared no-tests no-docs no-zlib no-apps -fPIC`,
  then `make build_libs && make install_dev`. `-fPIC` because the archive is
  linked into a shared object. `no-zlib` because it is the sole reason zlib
  was ever in the graph (§2). `no-apps`/`no-docs`/`no-tests` because nothing
  here needs the `openssl` CLI or its man pages.
* **ragel 6.10**: `CXXFLAGS="-O2 -std=c++03"`. Not cosmetic — the 2017 sources
  use the `register` storage class and implicit conversions that C++17
  removed, so a default-standard modern compiler rejects them.
* **yasm 1.3.0**: `CFLAGS="-O2 -std=gnu17 -Wno-implicit-function-declaration -Wno-int-conversion"`.
  Not cosmetic — observed failure without `-std=gnu17`:

  ```
  ./libyasm/bitvect.h:86:32: error: cannot use keyword 'false' as enumeration constant
     86 |         typedef enum boolean { false = FALSE, true = TRUE } boolean;
  ./libyasm/bitvect.h:86:32: note: 'false' is a keyword with '-std=c23' onwards
  ```

  Current gcc defaults to C23, where `false`/`true` are keywords.

The two generators are then copied to the one path the pinned tree reads:

```sh
mkdir -p "${BUILD_DIR}/bin"
cp -f "${TP_PREFIX}/bin/ragel" "${BUILD_DIR}/bin/ragel"
cp -f "${TP_PREFIX}/bin/yasm" "${BUILD_DIR}/bin/yasm"
```

**`cmake/openssl-target.cmake`** (new) — the like-for-like replacement for
`vendor/catboost/cmake/conan_provider.cmake`. It uses the same CMake API
Conan used (`cmake_language(SET_DEPENDENCY_PROVIDER ... SUPPORTED_METHODS
FIND_PACKAGE)`), so this is a swap of one provider for another, not a new
mechanism bolted on. It:

* hard-fails if `CATBOOSTR_OPENSSL_ROOT` is unset or if
  `include/openssl/ssl.h`, `lib/libssl.a` or `lib/libcrypto.a` is missing —
  **there is no system-openssl fallback**, because a silent fallback to an
  unpinned openssl is exactly the hole this ticket closes;
* defines `openssl::openssl` as an `INTERFACE IMPORTED GLOBAL` target pointing
  at the pinned static libraries;
* claims **only** `OpenSSL` in the provider; every other `find_package()` is
  left untouched and falls through to CMake's built-in implementation (which
  is why Python3/Cython resolution is unaffected).

## 5. Proof that Conan is out of the install path (Section IV step 6)

The ticket demands both conditions be *demonstrated*, not assumed. The
demonstration is stronger than asked: rather than only removing Conan's
network and cache, a **tripwire shim** was placed first on `PATH`, so any
attempt to invoke Conan is recorded and fails loudly.

### 5.1 The three conditions, all applied simultaneously

```sh
# (a) tripwire `conan` on PATH, FIRST -- shadows the real conan in the venv
$ cat <scratch>/shim/conan
#!/bin/sh
echo "TRIPWIRE: conan invoked: $*" >> "$CONAN_TRIPWIRE_LOG"
echo "conan: tripwire shim, refusing to run" >&2
exit 1

# (b) EMPTY cache: a fresh CONAN_HOME containing nothing but a remotes file
#     (no `p/` package store, no recipe cache, no default profile)
$ CONAN_HOME=<scratch>/fake_conan_home

# (c) UNREACHABLE remote
$ cat <scratch>/fake_conan_home/remotes.json
{"remotes": [{"name": "conancenter", "url": "https://conan-center.invalid.example/", "verify_ssl": true}]}
```

`.invalid` is an RFC 2606 reserved TLD; it cannot resolve.

Environment for the run: `PATH=<shim>:<venv>/bin:/usr/bin:/bin`,
`CATBOOSTR_JOBS=14`, fresh empty build directory, `Ninja` generator.
