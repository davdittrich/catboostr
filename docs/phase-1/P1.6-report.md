## 4. Getting `R CMD check --as-cran` to 0 ERRORs (Section IV steps 3, 7)

### 4.1 First real run: 1 ERROR (vendor/catboost not found)

`R CMD check --as-cran` extracts the tarball into a **fresh** directory
(`<outdir>/00_pkg_src/catboostr/`) and installs from there — `vendor/` is
correctly absent (§3), so `configure`'s own precondition check fires:

```
*** /home/dd/Gemini/p16-tmp/catboostr.Rcheck/00_pkg_src/catboostr/vendor/catboost not found -- this fork requires the pinned vendor/catboost snapshot.
ERROR: configuration failed for package 'catboostr'
Status: 1 ERROR, 1 NOTE
```

This is not a defect in `.Rbuildignore` — it is `configure`'s own
already-documented precondition (present since P1.4: "this fork requires the
pinned vendor/catboost snapshot"), exercised for the first time by an actual
`--as-cran` run against a real, isolated tarball extraction.

### 4.2 Second attempt: symlinking vendor/catboost in — WRONG, produces a new ERROR

To satisfy the precondition, `vendor/catboost` and `vendor/thirdparty` were
symlinked into the extracted `00_pkg_src/catboostr/vendor/` directory
(`--no-clean` preserves the extraction across a re-run; `tar` extraction
does not delete paths absent from the archive, so the symlinks survive). The
install then **succeeded** (4265/4265 build steps), but the check gained a
**new** ERROR:

```
* checking for portable file names ... WARNING
Found the following files with non-portable file names:
  vendor/catboost/catboost/tutorials/events/2020_odsc_west/ODSC West 2020 Kirillov CatBoost.pptx
  ...
ERROR
Found the following non-portable file paths:
  catboostr/vendor/catboost/.github/actions/upload_python_package_artifacts_for_all_py_versions/action.yaml
  catboostr/vendor/catboost/build/toolchains/cross-build.host.darwin.target.arm64-apple-darwin.clang.toolchain
  [72 lines omitted: 2 ERROR, 2 WARN, 7 INFO]
```

**Root cause, evidenced, not guessed:** `R CMD check` statically scans
**every file physically present** under the checked package directory for
CRAN-portability policy (path length, non-ASCII names, `.git` presence,
executable bits), regardless of what shipped in the tarball. Once
`vendor/catboost` physically exists anywhere inside that directory — even
via a symlink added after extraction, never part of the tarball — its
~870 MiB of **upstream CatBoost's own** long paths, non-ASCII filenames, and
`.git` metadata become failures attributed to **this package**. This is a
real, general fact about how `R CMD check` works, not specific to this
build.

**This is exactly why `.Rbuildignore` must exclude `vendor/` (§2/§3) — and
also why `vendor/catboost` must never be made visible inside the checked
directory by any means, not just the tarball.** The symlink approach was
therefore abandoned; per the anti-pivot guard, the fix had to address the
actual mechanism, not eyeball around the ERROR by trimming the symlinked
content.

### 4.3 The actual fix: `CATBOOSTR_VENDOR_SRC` / `CATBOOSTR_THIRDPARTY_SRC`

`configure` already resolves several inputs through env-var overrides with a
`${PKG_ROOT}`-relative default (`CATBOOSTR_BUILD_DIR`, `CATBOOSTR_JOBS`,
`CATBOOSTR_NINJA`, `CATBOOSTR_PYTHON3`, `CATBOOSTR_CYTHON`,
`CATBOOSTR_THIRDPARTY_PREFIX` — all pre-existing, from P1.4/P1.5). `VENDOR_SRC`
and `THIRDPARTY_SRC` were the only two build inputs still hardcoded to
`${PKG_ROOT}/...`. Two-line change, following the exact existing pattern:

```diff
-VENDOR_SRC="${PKG_ROOT}/vendor/catboost"
+VENDOR_SRC="${CATBOOSTR_VENDOR_SRC:-${PKG_ROOT}/vendor/catboost}"
...
-THIRDPARTY_SRC="${PKG_ROOT}/vendor/thirdparty"
+THIRDPARTY_SRC="${CATBOOSTR_THIRDPARTY_SRC:-${PKG_ROOT}/vendor/thirdparty}"
```

Local development behaviour is **unchanged** (both env vars unset →
identical default). For a check/CI run, point them at the real,
already-acquired checkout **outside** the checked directory entirely — no
file is added to, or symlinked into, the package tree at any point:

```
$ export CATBOOSTR_VENDOR_SRC=/home/dd/Gemini/catboost/vendor/catboost
$ export CATBOOSTR_THIRDPARTY_SRC=/home/dd/Gemini/catboost/vendor/thirdparty
$ R CMD check --as-cran catboostr_1.2.10.tar.gz
...
Status: 6 WARNINGs, 4 NOTEs
$ echo $?
0
```

**0 ERRORs.** `grep -n ERROR 00check.log` → only the summary line
`Status: 6 WARNINGs, 4 NOTEs` (no `ERROR` token). `checking tests ... OK`
(`Running 'testthat.R'`) confirms the 43-test suite (P1.8 baseline) still
passes end to end under `--as-cran`.

**Boundary note:** this is a 2-line change to a file not named in Section
IV, made under the explicit licence of step 7 ("Fix every ERROR ... until
zero remain") and Section VI's "0 ERRORs" Definition-of-Done item. It adds
no new mechanism (mirrors 6 pre-existing sibling env vars in the same file),
changes no default behaviour, and does not touch `vendor/catboost/` itself.
`git -C vendor/catboost status --porcelain` was empty before, during, and
after every run in this section.

**Confidence: 95** on the fix; **60** on whether CRAN's own build farm
would reach the same 0-ERROR state without an equivalent env-var pointed at
a pre-acquired `vendor/catboost` — CRAN's farm has no such mechanism to set
it, and the underlying architectural question ("how does an end-user or
CRAN obtain the ~870 MiB pinned CatBoost source with zero network access at
install time, given it cannot ship in the tarball without polluting every
future check the way §4.2 demonstrated") is **not resolved by this ticket**
and is flagged in §8 as a real, open, evidenced gap for follow-up ticketing

tested fix for *this ticket's own verification step* but is an operator-set
override, not an install-time mechanism a plain `install.packages()` user
or CRAN's farm could invoke. **Confidence: 90** this gap is real (directly
evidenced by §4.1-4.2); **not scored** on how to close it — that is a design
decision for a future ticket, not a finding this one can respond to without
