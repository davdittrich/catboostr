# P1.7: Offline install test in rootless Podman container

**Ticket:** catboost-8z4.15
**Repo:** `/home/dd/Gemini/catboost`, branch `phase-0`
**Environment:** a 2-CPU network-isolated Linux container (rootless Podman +
crun, cgroup v2, systemd cgroup manager, host: 32-core AMD, kernel per
`podman info`). Not CRAN's or a CRAN-proxy environment — CRAN's own
check-farm runtime specs are unverifiable from public sources and are
irrelevant now that CRAN distribution is out of scope (2026-07-31 decision).

## 1. What was built, and where

Two phases, deliberately kept separate:

1. **Image build (network allowed).** `Containerfile` (below), based on
   `docker.io/rocker/r-ver:4.6.1` (Ubuntu 24.04 "noble", R 4.6.1 — matches
   the epic's pinned R baseline). Installs OS build tools via `apt-get`
   (`clang lld cmake make python3 cython3 perl git ca-certificates procps
   curl iproute2`), installs the one R-level runtime dependency
   (`jsonlite`, from `DESCRIPTION`'s `Imports:`) via
   `install.packages(repos='https://cloud.r-project.org')`, copies in only
   the package-relevant paths (`configure DESCRIPTION NAMESPACE
   .Rbuildignore R/ src/ man/ cmake/ inst/ tools/vendor/` — explicitly NOT
   `tools/oracle/` (899 MiB, irrelevant to install) and NOT any host
   `vendor/` — see below), then runs
   `tools/vendor/acquire.sh && tools/vendor/acquire-thirdparty.sh` *inside
   the build stage*, with network, simulating "user already ran the acquire
   scripts before sealing the image." The image is then sealed (`podman
   build` commits the layer).
2. **Timed/isolated install (network refused).** `podman run --network=none
   --cpus=2 <image> bash /in-container-install.sh`, run three times, each
   against a **fresh container instantiated from the same sealed image**
   (podman gives every `run` its own ephemeral writable layer — this is
   what guarantees "no pre-existing build venv, pip cache, or prior build
   artifacts" for each of the three timed runs, see §4).

Exact `Containerfile` used (context = a scratch copy containing only the
paths above, to avoid tarring the 1.3 GiB host `vendor/catboost` into the
build context uselessly):

```dockerfile
FROM docker.io/rocker/r-ver:4.6.1
ENV DEBIAN_FRONTEND=noninteractive
ENV CC=clang
ENV CXX=clang++
RUN apt-get update -qq \
    && apt-get install -y -qq --no-install-recommends \
       clang lld cmake make python3 cython3 perl git ca-certificates procps curl iproute2 \
    && rm -rf /var/lib/apt/lists/*
RUN R -e "install.packages('jsonlite', repos='https://cloud.r-project.org')" \
    && R -e "if (!requireNamespace('jsonlite', quietly=TRUE)) quit(status=1)"
WORKDIR /repo
COPY configure DESCRIPTION NAMESPACE .Rbuildignore /repo/
COPY R/ /repo/R/
COPY src/ /repo/src/
COPY man/ /repo/man/
COPY cmake/ /repo/cmake/
COPY inst/ /repo/inst/
COPY tools/ /repo/tools/
RUN tools/vendor/acquire.sh /repo/vendor/catboost \
    && tools/vendor/acquire-thirdparty.sh /repo/vendor/thirdparty
RUN rm -rf inst/libs src/*.o src/*.so \
    && test ! -d /root/.cache/pip \
    && test ! -f inst/libs/libcatboostr.so
```

`ENV CC=clang / CXX=clang++` is pinned globally because the third-party
subbuilds that `configure` drives (openssl/ragel/yasm) do not set `CC`/`CXX`
themselves and this image has no `gcc` at all — pinning avoids relying on
autoconf's own compiler-search order, and matches P1.4's finding that only
clang can compile the pinned `vendor/catboost` tree.

`cython3`'s apt package installs a `cython` binary directly (verified:
`dpkg -L cython3 | grep bin` lists `/usr/bin/cython` alongside
`/usr/bin/cython3`), so no `CATBOOSTR_CYTHON` override or venv was needed.

## 3. Network isolation, per run

Each of the three runs independently confirmed, before touching the build,
that the container has no route out. Quoted from run 1 (identical outcome
in runs 2 and 3):

```
$ timeout 3 bash -c 'echo > /dev/tcp/8.8.8.8/53'
bash: connect: Network is unreachable
bash: line 1: /dev/tcp/8.8.8.8/53: Network is unreachable
$ ip -o addr show
1: lo    inet 127.0.0.1/8 scope host lo
1: lo    inet6 ::1/128 scope host
```

Only `lo` exists — no other interface, no default route, connect() itself
fails at the kernel level with `ENETUNREACH` ("Network is unreachable"),
not a DNS or TLS failure. `--network=none` gives the container loopback
only, exactly as claimed.

`podman info` (host-level, quoted once, applies to all three runs):

```
rootlessNetworkCmd: pasta
security:
  rootless: true
```

`cgroup.controllers`/`cpuset` limitation and the `--cpus=2` mechanism were
already independently verified in prior tickets (quoted again here per-run
for completeness):

```
$ cat /sys/fs/cgroup/cpu.max
200000 100000
```

This is the CPU budget mechanism: 200ms of CPU time per 100ms period = 2
CPU-equivalents, enforced by the kernel cgroup v2 CPU controller regardless
of what `nproc` reports inside the container:

```
$ nproc
32
```

`nproc` is confirmed misleading exactly as the ticket states — the 2-CPU
constraint is real (cgroup-enforced) but not visible to code that
auto-detects parallelism from `nproc`. This is why `configure` never calls
`nproc`: `CATBOOSTR_JOBS` defaults to a hardcoded `4`, and this run
explicitly overrides it to `2` (see §4).

## 4. Explicit parallelism — mechanism correction (disclosed, not silently substituted)

The ticket's reference list names three variables to export:
`CMAKE_BUILD_PARALLEL_LEVEL=2`, `MAKEFLAGS=-j2`, and R's `Ncpus=2`. All
three were exported. **None of the three is actually read by this
repository's `configure`** — this is stated explicitly rather than left
implicit:

- `configure` never invokes `cmake --build` (the only command
  `CMAKE_BUILD_PARALLEL_LEVEL` affects) — it calls `ninja`/`make` directly.
- `configure`'s explicit `-j"$JOBS"` argument to `make`/`ninja`
  (`configure:257,272,290,421`) overrides any inherited `MAKEFLAGS`.
- `Ncpus` is an `install.packages()` knob for installing multiple packages
  in parallel; it has no effect on a single package's own C++ compile step.

The variable `configure` actually reads is `CATBOOSTR_JOBS`
(`configure:200`, `JOBS="${CATBOOSTR_JOBS:-4}"`), passed as `-j"$JOBS"` to
every `make`/`ninja` invocation (third-party subbuilds and the main CMake
build alike). **This is the one that was set to `2`** in
`in-container-install.sh`:

```sh
export CATBOOSTR_JOBS=2
export CMAKE_BUILD_PARALLEL_LEVEL=2   # not read by this configure; exported anyway
export MAKEFLAGS=-j2                  # not read as the effective value; exported anyway
export R_PROFILE_USER=/tmp/Rprofile.p17   # options(Ncpus = 2)
```

Leaving `CATBOOSTR_JOBS` at its default (`4`) would have silently
requested 4-way parallelism inside a 2-CPU-equivalent cgroup — exactly the
"one `nproc`-reading layer silently restores 32 jobs" failure mode the
ticket warns against, except via a hardcoded default rather than
auto-detection. This was caught and corrected before running the timed
test, not discovered by it.

## 5. Peak concurrent compiler processes — measured, not assumed

Instrumentation: a background poll loop sampling
`pgrep -x -c 'clang|clang\+\+'` every 0.2s for the full duration of `R CMD
INSTALL`, tracking the maximum observed count (`in-container-install.sh`).
Verified against a real (not renamed-via-argv0) clang invocation before
trusting it: `ps -eo comm` shows `comm=clang` for a running `clang -c`
process, confirming `pgrep -x` on process name correctly matches the real
compiler binary.

**Measured peak, all three runs: 3.** This exceeds the ticket's `<= 2`
budget. Quoted:

```
run1: P17_PEAK_PARALLEL=3
run2: P17_PEAK_PARALLEL=3
run3: P17_PEAK_PARALLEL=3
```

**`parallelism_assertion_held: false.`** This is reported as a genuine
finding, not smoothed over. Root cause was not proven — proving it exactly
would need finer-grained process-lifecycle tracing than a 0.2s poll loop
provides, and no attempt is made here to claim a mechanism that wasn't
directly observed. What is directly established (confidence 90, from the
`cpu.max` read quoted in §3, present and re-checked in every run): the
**cgroup CPU quota independently caps total CPU consumption at 2
CPU-equivalents regardless of instantaneous process count** — so even if a
third `clang`/`clang++` process transiently existed (e.g. one job's process
not yet reaped by `make`'s job-server bookkeeping while the next job's
process had already been forked — a common `fork()`-before-`waitpid()`
race under GNU Make's `-jN` job control), the kernel still would not have
scheduled more than 2 CPU-equivalents of work across them at any instant.
That specific causal claim (zombie/fork-before-reap race) is a hypothesis
consistent with the evidence, not a directly observed fact (confidence 55,
flagged for review) — it is offered as the most likely explanation given
that all three independent runs measured exactly 3, never higher, which is
more consistent with a narrow, repeatable process-bookkeeping window than
with unconstrained parallelism (an unconstrained build on this 32-core
host would be expected to spike far above 3). No further build-system
instrumentation was added to confirm this beyond what's stated here, per
the ticket's own time/scope framing — this is disclosed as an open
follow-up, not resolved.
