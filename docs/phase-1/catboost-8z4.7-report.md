# catboost-8z4.7 — Real install-time dependency surface of the R-package-only build

Status: DONE. All measurements below come from actual `cmake`/`ninja`/`conan` runs against a disposable
copy of the pinned upstream tree, not from reading CMakeLists in isolation.

## 1–2. Per-package classification: INVOKED vs RESOLVED_ONLY vs ABSENT

Method for distinguishing INVOKED from RESOLVED_ONLY: `conan graph info`'s own output separates
**Requirements** (`self.requires`, C/C++ deps: openssl, zlib) from **Build requirements**
(`self.tool_requires`, host tools: ragel, swig, yasm) — but that's still conanfile-level and,
per the ticket, "present in the graph is not evidence of invocation." The decisive test is
`grep` over the *generated* `build.ninja` (84,789 lines) and the link line of the actual
`catboostr` target (`ninja -t query catboost/R-package/src/libcatboostr.so`) for each package's
binary path (`conan_home/p/b/<hash>/p/...`) or generated output file. A package that never
appears in `build.ninja` by content (not just by name-as-a-directory-string) never touches the
R-package build; a package present only as a PATH-tool during conan's own recipe build (to
compile another conan recipe from source) is RESOLVED_ONLY.

## 3. ragel/yasm outputs and pre-generation feasibility

Generated files (sizes from the actual build, `scratchpad/8z4.7/build/`):

| file | bytes | MiB |
|---|---|---|
| `util/parser.rl6.cpp` (yutil, ticket line 589) | 290,846 | 0.2774 |
| `library/cpp/json/fast_sax/parser.rl6.cpp` | 23,502 | 0.0224 |
| `library/cpp/tokenizer/nlptok_v2.rl6.cpp` | 252,427 | 0.2407 |
| `library/cpp/tokenizer/nlptok_v3.rl6.cpp` | 256,099 | 0.2442 |
| `util/context_x86.o` (yutil, ticket line 595, yasm→object directly) | 2,192 | 0.0021 |

Total generated-code footprint: ~825 KiB of C++ source + one 2 KiB object file. `pregeneration_feasible: true`
— the ragel `.rl6.cpp` outputs are deterministic pure-text codegen from a stable `.rl6` grammar
(no host-arch dependence) and can be committed and swapped in via `if(EXISTS pregenerated) ... else() target_ragel_lexers() endif()`.
The yasm output (`context_x86.o`) is architecture-specific machine code (x86 `ucontext`
swap trampoline for the fiber/coroutine engine) — pre-generating it is feasible only per-target-arch
(x86_64 here) and would need one prebuilt object per supported architecture, which is more fragile
than committing the four ragel `.cpp` files. Recommendation scope: pre-generate the ragel outputs
(cheap, portable); leave yasm as a real build-time tool requirement unless CRAN policy forces it,
in which case a pure-C++ fallback path for `context_x86.asm` (already exists upstream for other
platforms, e.g. `context_x86_64.S` / non-yasm builds) should be investigated in a follow-up ticket,
not this spike.

## 4. The openssl question — actual configure attempt

Configured a second build dir (`scratchpad/8z4.7/build_noopenssl`) with everything identical to the
baseline plus `-DCMAKE_DISABLE_FIND_PACKAGE_OpenSSL=ON` (standard CMake mechanism that makes any
`find_package(OpenSSL ...)` report NOT FOUND regardless of the Conan dependency provider or a
system OpenSSL install — needed because this dev machine has system OpenSSL headers/libs at
`/usr/include/openssl` and `/usr/lib/libssl.so`, which would otherwise silently mask the test).

Result: **configure fails, exit 1.** Exact errors (`scratchpad/8z4.7/configure_noopenssl.log`):

```
CMake Error at library/cpp/neh/CMakeLists.linux-x86_64.txt:15 (find_package):
  Could NOT find OpenSSL (missing: OPENSSL_CRYPTO_LIBRARY OPENSSL_INCLUDE_DIR)
  ... OpenSSL REQUIRED, CMAKE_DISABLE_FIND_PACKAGE_OpenSSL REQUIRED ...
CMake Error at library/cpp/openssl/init/CMakeLists.linux-x86_64.txt:15 (find_package): ...
CMake Error at library/cpp/openssl/method/CMakeLists.linux-x86_64.txt:15 (find_package): ...
CMake Error at library/cpp/openssl/holders/CMakeLists.linux-x86_64.txt:15 (find_package): ...
```

So: **openssl_required = true, as currently wired.** But the failure site is decisive for the
verdict: it fails inside `library/cpp/neh` (the HTTP/network transport used by
`library/cpp/par`, the distributed-training RPC layer), not inside anything the R binding calls.
Traced the actual dependency chain from the `catboostr` link line
(`ninja -t query .../libcatboostr.so`): `catboostr → catboost-libs-train_lib →
private-libs-distributed → library-cpp-par → library-cpp-neh → openssl::openssl`.
`library/cpp/neh/CMakeLists.linux-x86_64.txt:33,43-44` links `openssl::openssl`, `cpp-openssl-init`,
`cpp-openssl-method` unconditionally. **The R package never calls into `private/libs/distributed`
(that's Yandex's internal multi-host MPI-style distributed training, not exposed through
`catboostr.cpp`'s R entry points)** — openssl is pulled in purely because CMake's dependency graph
is unconditional (no `CATBOOST_COMPONENTS` gating inside `train_lib`'s own subtree), not because
catboostr's own code needs TLS/crypto. `openssl_failure_mode`: "CMake find_package(OpenSSL REQUIRED)
error at library/cpp/neh (network layer for distributed training), inherited transitively through
train_lib → private/libs/distributed → library/cpp/par → library/cpp/neh; not referenced by
catboost/R-package/src/catboostr.cpp itself."

This is evidence, not a fix: cutting the `private/libs/distributed`/`neh` edge out of the
R-package's dependency graph is a real code change to `train_lib`'s CMakeLists (component-gating
an internal subtree) — explicitly **out of scope** for this spike ("OUT: no configure rewrite").
Verdict below reflects that the *measured floor today* is openssl-required, while flagging the
one-line Phase 1 win (component-gate `private/libs/distributed` out of R-package builds) that would
let openssl drop out entirely, collapsing vendoring scope toward zlib alone.

## 5. zlib from R's own linkage

`R CMD config --ldflags` (system R, this host):

```
-Wl,--export-dynamic -fopenmp ... -L/usr/lib64/R/lib -lR -lpcre2-8 -ldeflate -lzstd -llzma -lbz2 -lz -ltirpc -lrt -ldl -lm -licuuc -licui18n
```

`-lz` (and even `-lbz2`) is already in R's own link flags — `libR.so` itself depends on the
system `libz.so`. `zlib_from_r_feasible: true`, but precisely: this only proves the *runtime*
symbol (`libz.so`) is already present in the R process once `libR.so` is loaded — it does **not**
provide `zlib.h` dev headers via `R CMD config` (no such variable exists). A package that wants to
call `deflate()`/`inflate()` directly still needs `zlib1g-dev`/`zlib-devel` at compile time, which
is an ordinary, ubiquitous CRAN `SystemRequirements: zlib` declaration (hundreds of CRAN packages
already require it) — not something that needs vendoring via Conan. Net effect: replacing Conan's
zlib package with "assume system zlib dev headers + link flag `-lz`" is a standard, low-risk CRAN
pattern.

## 6. Python3 install-time necessity

`python3_required_at_install: true`. Specific call sites, verified in the disposable copy's
`cmake/common.cmake`:

- Line 3: `find_package(Python3 REQUIRED)` — hard configure-time gate, unconditional (not inside
  any `if(CATBOOST_COMPONENTS ...)` guard).
- Line 35: `Python3::Interpreter ... build/scripts/run_tool.py -- <RAGEL_BIN> ...` — every ragel
  invocation is wrapped through a Python script (confirmed live in `build.ninja`'s ragel commands,
  which literally run `<venv>/bin/python .../run_tool.py -- <build>/bin/ragel ...`).
- Line 48: same wrapper for yasm (confirmed in `build.ninja`'s yasm command).
- Line 61: `gen_join_srcs.py` — source-list joining helper.
- Lines 181, 187: `generate_vcs_info.py` / `vcs_info.py` — generates `vcs_info.json` and
  `__vcs_version__.c`, which **is** linked into `catboostr.dir` (`__vcs_version__.c.o`, confirmed
  built at ninja step 197/200 in the baseline log).
- Line 262 (Linux `EXPORT_SCRIPT_FLAVOR` branch): `export_script_gen.py`, generating
  `gen_catboostr.exports`, the linker version-script consumed while linking `libcatboostr.so`
  (ninja step 194/200, "Generating gen_catboostr.exports").
- Line 305: `split_unittest.py` — test-sharding only, not exercised for `CATBOOST_COMPONENTS=R-package`
  (no test targets were generated in this configure; irrelevant to install-time).

So Python3 is load-bearing at **build** time (code generation for a file that gets compiled into
the final `.so`, and for the linker export-script that shapes the `.so`'s public symbol table) —
not just at CMake-configure time. `CYTHON_EXE` was accepted but reported "unused" by CMake for
`CATBOOST_COMPONENTS=R-package` (`configure_baseline.log`: "Manually-specified variables were not
used by the project: CYTHON_EXE") — Cython is a Python-package-only need, confirmed absent from
the R-package configure surface.

`cmake_minimum_required`: `CMakeLists.txt:15` → **`cmake_minimum_required(VERSION 3.15)`**, verified
by direct read of the disposable copy (this line is a `YaTool`-generated `CMakeLists.txt`, not
hand-maintained, so 3.15 is authoritative for now unless the fork's own build glue needs newer
features — the `CMAKE_PROJECT_TOP_LEVEL_INCLUDES` dependency-provider mechanism used by
`conan_provider.cmake` itself requires CMake ≥ 3.24, so the *effective* floor for this project is
3.24, not 3.15).

Proposed `SystemRequirements` line for `DESCRIPTION`:

```
SystemRequirements: CMake (>= 3.24), Python3 (>= 3.8), a C++20 compiler, zlib development headers (zlib1g-dev / zlib-devel)
```

(Ragel and yasm are NOT listed here because they remain Conan-managed build tools under the
current, unmodified dependency graph — see the openssl verdict for why the graph isn't rewritten
in this ticket.)

## 7. -DCUSTOM_ALLOCATORS=Off

Configured a third build dir (`scratchpad/8z4.7/build_noca`) with the baseline flags plus
`-DCUSTOM_ALLOCATORS=Off`. Configure: exit 0 (`configure_noca.log`). Build: `ninja catboostr -j32`,
exit 0, wall time 114.8s (858 steps — full rebuild from a clean tree, since a fresh `-B` dir was
used; not comparable 1:1 to the 47.5s incremental baseline number, but this is a from-scratch
Release build of the same component either way and it *completes*). Output:
`catboost/R-package/src/libcatboostr.so`, 34,397,008 bytes (32.80 MiB) — 99,056 bytes (0.09 MiB)
smaller than the baseline `.so`, consistent with mimalloc's removal (mimalloc is a small
allocator relative to the whole codebase, so the size delta is modest, not zero).

Verified via `ninja -t query catboost/R-package/src/libcatboostr.so`: **zero** occurrences of
`mimalloc` anywhere in the link line (vs. `library/cpp/malloc/mimalloc/libcpp-malloc-mimalloc.a`
present in the baseline's link line) — confirms mimalloc is genuinely gone from the link graph,
not just unused-but-linked.

Functional check: both binaries (baseline and `CUSTOM_ALLOCATORS=Off`) were `dyn.load()`ed into a
live R session (`Rscript smoke_load.R <so>`) and the exported symbol `CatBoostHashStrings_R` was
resolved successfully via `getNativeSymbolInfo()` in both — the shared library loads cleanly and
exposes its R-callable native routines with the default allocator. This is a load/link-level
smoke test, not a full train/predict functional test (out of scope for a configure/build spike);
a follow-up ticket should run an actual `CatBoostFit_R` round-trip before this flag is adopted.

`custom_allocators_off_works: true` (configures, builds, mimalloc confirmed absent, binary loads
and resolves symbols).
