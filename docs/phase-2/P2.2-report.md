## 1. Canonical-JSON serialization contract (`to_canonical`)

- **Key ordering:** dict keys sorted lexicographically, recursively.
  Serialized with `json.dumps(..., sort_keys=True)`. Key order carries no
  semantic meaning in R's or the oracle's native output, so sorting makes
  the canonical string deterministic regardless of source-side dict
  ordering. Confidence 90 — mechanical, no ambiguity.
- **List order:** kept, **not** sorted. Lists represent semantically
  ordered sequences (a tree's left/right child order,
  `calc_feature_statistics`'s per-bin sequence), so reordering would
  silently break a genuine differential test. Confidence 90.
- **Numeric leaves:** kept as Python `int`/`float`. `NaN`/`+Inf`/`-Inf`
  have no JSON literal, so they are tagged as
  `{"__float__": "NaN"|"Infinity"|"-Infinity"}` before serialization
  (`json.dumps(..., allow_nan=False)` is used deliberately, so a raw float
  special reaching the dumper is a caught bug, not a silent `NaN` in the
  output). Confidence 85 — this is a design choice (tagged wrapper vs. a
  string sentinel); documented, not hidden.
- **Nested/recursive structures:** kept **nested**, never flattened.
  Addressed via `resolve_path()`'s dotted-path-plus-`[]`-broadcast syntax
  (e.g. `children[].value` walks every element of a `children` list at
  arbitrary depth). This is the direct answer to ticket III's Anti-pivot
  guard.

## 2. Anti-pivot guard check (recursive/tree structures)

**Guard text:** "If the canonical-JSON design can't cleanly represent some
structural output (nested/recursive tree structures, e.g. `plot_tree`),
STOP, document the specific representational gap with a confidence score,
and propose the resolution."

**Finding: no stop triggered.** JSON's native `dict`/`list` nesting
represents an arbitrarily deep recursive tree without loss — a
`plot_tree`-shaped node (`{"feature": ..., "left": {...}, "right":
{...}}`) round-trips through `to_canonical()` unchanged in structure.
`resolve_path()`'s `[]` broadcast addresses a list at any depth, so a
mapping can walk `nodes[].split.feature` etc. without a flattening pass.
Confidence 85. One nuance recorded, not a gap: if R's and the oracle's
child-array elements were ever emitted in different but semantically
equivalent order (e.g. sorted by name instead of split order), a
positional list comparison would false-negative. Not observed as an issue
here — CatBoost's tree traversal order is deterministic in both R and
Python (same underlying C++ core) — but it is exactly the kind of
first-principles case future differential-test authors must check before
declaring a `bins[]`/`nodes[]`-shaped mapping. Recorded as a documented
watch-item in `structural_mapping.py`'s module docstring, not implemented
as a design feature (would be speculative — no observed need).
`representational_gaps_found: []` in the output schema below, because
this was resolved by the existing broadcast design, not left open.

## 3. Field-mapping declaration schema

JSON (matches the repo's existing fixture format; no new dependency).
Per capability: `{"capability": str, "schema_version": 1, "fields": [...]}`.
Each field entry declares, per ticket III Logic guard:

- (a) `r_field` / `oracle_field` — dotted-path correspondence.
- (b) `compare`: `"exact"` or `"numeric"` (with `tolerance: {oracle,
  value}` for numeric — reuses `build_matrix.DEFAULT_TOLERANCE`
  (`{"python": 1e-12, "cli": 1e-9}`) and `CLI_PRECISION_FLOOR` (`1e-9`)
  verbatim; no new tolerance regime, per ticket and §4.3).
- (c) `exclude` / `exclude_reason` for intentionally non-comparable
  leaves (e.g. a timestamp).

`validate_mapping()` enforces this is present for every field —
schema-level, raises `ValueError`, does not silently accept a partial
declaration. See `tools/parity/mappings/example_worked.json`.

Note the deliberate distinction: a **broken mapping** (missing field,
numeric-declared-as-exact) raises `ValueError` — a bug in the
declaration. A **perturbed value** on an otherwise-valid mapping returns
`(False, [mismatch...])` — a normal differential-test red result, not an
exception. Conflating these would make a genuinely red test
indistinguishable from a broken harness.

## Post-review fix: NaN vs NaN false mismatch

**Bug (reviewer-caught):** `compare()`'s numeric branch called
`math.isclose(r_f, o_f, rel_tol=tol)` directly. Per IEEE-754,
`math.isclose(nan, nan)` is `False`, so a leaf where R and the oracle both
legitimately emit `NaN` (e.g. `calc_feature_statistics` on an empty bin --
exactly the capability class this mechanism targets) was reported as a
mismatch even though both sides agree. The `to_canonical()`/tagging side
was correct; the comparator didn't complete the contract described in §1.

**Fix** (`tools/parity/structural_mapping.py`, in `compare()`'s numeric
branch): NaN-aware equality checked before falling back to
`math.isclose` --

```python
is_close = (math.isnan(r_f) and math.isnan(o_f)) or math.isclose(
    r_f, o_f, rel_tol=tol
)
if not is_close:
    mismatches.append(...)
```

Both-NaN now counts as a match; NaN-vs-number still correctly falls
through to `math.isclose` (which is `False` whenever exactly one operand
is NaN), so it still mismatches.

**Covering tests added** (`tools/parity/test_structural_mapping.py`,
class `TestWorkedExample`):
- `test_both_sides_nan_is_a_match_not_a_mismatch` -- both `r_doc` and
  `oracle_doc` set the same leaf to `math.nan`; asserts `compare()`
  returns `(True, [])`.
- `test_nan_vs_number_is_a_mismatch` -- only the R-side leaf is `nan`,
  oracle side keeps its real number; asserts `compare()` returns
  `(False, [...])`.

Neither test existed before (the original suite only exercised NaN
through `to_canonical()`, never through `compare()`, which is why the bug
wasn't caught pre-review).

**Direct reproduction of the reviewer's exact repro, before/after:**

```
$ python3 - <<'EOF'
import math, structural_mapping as sm
mapping = {"fields": [{"r_field": "v", "oracle_field": "v", "compare": "numeric",
                        "tolerance": {"oracle": "python", "value": 1e-12}}]}
print(sm.compare(mapping, {"v": math.nan}, {"v": math.nan}))
print(sm.compare(mapping, {"v": math.nan}, {"v": 1.0}))
EOF
(True, [])
(False, ['v[0]: numeric mismatch nan vs 1.0 (rel_tol=1e-12)'])
```

Matches the required contract: NaN==NaN is a match, NaN-vs-number is a
mismatch.
