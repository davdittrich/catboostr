## 1. Method

All 725 rows of `tests/fixtures/parity/matrix.json` were run through four
mechanical rules, applied in the priority order actually implemented by P2.1's
`tools/parity/build_matrix.py::determine_method()` (universal checked first —
confirmed against that function's source, not re-derived from
`capability_diff.json`):

1. `universal == true` (or `method == "non_capability"`) → **universal flag**.
2. `kind in (parameter, flag)` → **parameter/flag family**.
3. `kind == enum_member` → **enum-member attachment**.
4. Everything else (`kind` in `method`/`mode`/`submode`/`function`/`class`/
   `property`/`attribute`, including every row P2.1 left as
   `needs_disposition: true`) → **method/mode-shaped candidate**.

Build script: `tools/parity/apply_disposition.py` (committed, re-runnable
against `tests/fixtures/parity/matrix.json` and
`tests/fixtures/parity/disposition_judgments.json` to regenerate
`tests/fixtures/parity/matrix.dispositioned.json` byte-for-byte; pinned by
`tools/parity/test_apply_disposition.py`).

Output artifact: **`tests/fixtures/parity/matrix.dispositioned.json`** — all
725 original rows, with `method` and `needs_disposition` rewritten on the
330 method/mode-shaped rows P2.1 left as `method: null` (resolved to a final
output-type below) and `tolerance` populated on the 274 of those rows whose
final method is `elementwise` (Sec 4.3's own default per oracle, reused
verbatim from `build_matrix.DEFAULT_TOLERANCE` — no new tolerance value is
invented, so no `tolerance_justification` is required), plus:

- `disposition`: one of `universal_flag` / `parameter_flag_family` /
  `enum_member_attachment` / `method_mode_shaped` / `unclear`
- `disposition_rule`: which rule fired
- `disposition_confidence`: 100 for the three mechanical categories, 95 for
  the method/mode-shaped catch-all (mechanical rule, but "catch-all" by
  construction so scored one notch below a positive-match rule)
- `family_id` / `family_size` (parameter/flag rows only) — `family_id` is
  simply the row's own `inventory_row_id`, which P2.1 already deduplicated to
  one row per family; `family_size` is `len(members)`.
- `attached_to` (enum-member rows only) — copied verbatim from
  `members[0].owner`.
- For method/mode-shaped rows: `method` is resolved from `null` to a final
  §4.3 output-type (`elementwise` / `roundtrip` / `structural` / `snapshot` /
  `error_class`), plus `final_method_confidence` (0–100) and
  `final_method_note` recording the reasoning for every non-mechanical call.
  The 8 rows P2.1 already tagged `method: structural` by exact name-match
  against spec §4.3's two named examples (`plot_tree`,
  `calc_feature_statistics`) keep that value at confidence 95 (mechanical,
  spec-named) and are not re-judged.

## 7. Confidence and findings requiring attention at sign-off

80 of the 338 method/mode-shaped rows got a `final_method_confidence` below
60 (i.e., the output-type call is a judgment call worth the reviewer's
scrutiny, not a mechanical fact). Full list is in the JSON artifact
(`final_method_confidence < 60`); the clusters worth flagging explicitly:

**a) State-mutator methods (`set_*`), ~45 rows, confidence 50.** Methods like
`set_params`, `set_feature_names`, `set_scale_and_bias`, `Pool.set_baseline`,
`Pool.set_group_id`, etc. have no output of their own — spec §4.3's five
categories (elementwise/roundtrip/structural/snapshot/error_class) don't
have a "state mutator, verified via paired getter" bucket. Tagged
`elementwise` as the nearest fit, but the real test design (call setter, then
call the paired getter, compare) is a Phase 3 design decision, not decided
here.

**b) `fit` itself (×4 classes), confidence 45.** `fit` produces no comparable
output of its own; parity is established transitively through every other
getter/predict row on the fitted model. Tagged `elementwise` as a
placeholder — flagging rather than force-fitting per the ticket's Anti-pivot
guard.

**c) `compare` (×4 classes), confidence 50.** Renders an interactive
model-comparison widget in Python (no direct precedent in spec §4.3's table).
Tagged `structural` as the closest fit, but this is the weakest structural
call in the set.

**d) Likely introspection artifacts, 12 rows, confidence 25 — needs
triage before Phase 3.** These are Python module members that are almost
certainly leaked imports or internal helpers rather than real catboost
capabilities (visible from `inventory_row_id` and `kind` alone, no
`capability_diff.json` re-derivation used):

```

catboost.utils.PATH_TYPES             -- type-tuple constant, internal isinstance-check helper
catboost.utils.contextmanager         -- stdlib contextlib.contextmanager, leaked via import
catboost.utils.defaultdict            -- stdlib collections.defaultdict, leaked via import
catboost.utils.fspath                 -- stdlib os.fspath, leaked via import
catboost.utils.pl                     -- third-party polars module, leaked via conditional import
catboost.utils.polars                 -- third-party polars module, leaked via conditional import
catboost.eval.copy                    -- stdlib copy module, leaked via import
catboost.eval.make_dirs_if_not_exists -- filesystem side-effect helper, no comparable output; possibly not public API at all
catboost.datasets.PATH_TYPES          -- type-tuple constant, internal isinstance-check helper
catboost.datasets.fspath              -- stdlib os.fspath, leaked via import
catboost.datasets.logger              -- a logging.Logger instance, leaked via module attribute
```

These fall mechanically into `method_mode_shaped` (rule 4, "everything
else") because the four-category test has no separate bucket for
introspection noise — flagging them here rather than inventing a fifth
disposition category or silently dropping them. **Recommendation for Phase 3
triage: confirm these are not real API surface before writing a
differential test for any of them** — most likely they should never become
individual tickets at all, but that determination is explicitly out of this
ticket's boundary (it is itself a piece of "the genuine feature work"
requiring a decision, i.e. Phase 3+).

**e) `catboost.eval.*` cluster (13 classes + 7 functions, ~20 rows),
confidence 40–55.** The `catboost.eval` (feature-evaluation / `Evaluate`)
subsystem is a distinct, rarely-used part of the public Python surface. Some
of its classes (`FactorUtils`, `FoldModelsHandler`) may not be intended as
public API at all — flagged at confidence 40, the lowest of the
non-introspection-artifact rows. No recommendation is made about whether
these should be one ticket or twenty; that is a Phase 3+ scope decision.

**f) `catboost.CatboostError` (lower-case "b"), confidence 85.** A second
exception-class row exists alongside `catboost.CatBoostError`. Almost
certainly an intentional backward-compat alias (this pattern exists in
upstream CatBoost's Python package), not a typo in the matrix — but worth a
human glance before Phase 3 treats it as a second, independent capability.

## 11. Correction (whole-branch review)

Whole-branch review found three defects, now fixed:

1. **`needs_disposition`/`method` disagreement.** The 330 rows whose `method`
   was rewritten from `null` to a concrete final method still carried
   `needs_disposition: true`, contradicting `build_matrix.py`'s own
   `needs_disposition: method is None` invariant. `tools/parity/apply_disposition.py`
   now recomputes `needs_disposition` from the post-rewrite `method`, so the
   two fields can never disagree.
2. **Unpopulated `tolerance` on `elementwise` rows.** All 274 rows whose final
   method is `elementwise` had `tolerance: null`, so the precision-ceiling and
   tolerance-justification guards in `build_matrix.py` were never exercised
   against real disposition data. `apply_disposition.py` now sets
   `tolerance = build_matrix.DEFAULT_TOLERANCE[oracle]` on every `elementwise`
   row — reusing the two existing spec defaults verbatim, so no
   `tolerance_justification` is required.
3. **Throwaway build script, no pinning test.** The script that produced
   `matrix.dispositioned.json` lived only in `/tmp` and was not re-runnable.
   It is now `tools/parity/apply_disposition.py` (committed), driven by a
   committed judgment-data fixture (`tests/fixtures/parity/disposition_judgments.json`,
   the per-row `final_method`/`final_method_confidence`/`final_method_note`
   values for the 330 non-mechanical method/mode-shaped rows), and pinned by
   `tools/parity/test_apply_disposition.py`, which rebuilds
   `capability_diff.json` → `matrix.json` → `matrix.dispositioned.json` and
   asserts the result is byte-for-byte identical to the committed artifact.

Also backfilled the one `final_method_note` missing on a
confidence-under-60 row (`mode:model-based-eval`, confidence 55): it now
records that the CLI mode compares an evaluated model's per-object loss
against a baseline via bootstrap and prints numeric statistics (hence
`elementwise`), with confidence held below 60 because its exact combined
summary/per-fold stdout layout has not been inspected against a real run.

Re-ran `apply_disposition.py` after these fixes and confirmed the category
counts are unchanged: `parameter_flag_family: 361` (139 parameter + 222 CLI
flag families), `enum_member_attachment: 24`, `universal_flag: 2`,
`method_mode_shaped: 338` — total `725`. The only per-row deltas are the 330
`needs_disposition` flips, the 274 `tolerance` fills, and the 1
`final_method_note` backfill above; every other field on every row is
unchanged from the prior artifact.
