## Finding 1: `get_object_importance` on `MultiClass` (upstream #869)

**Reproduced: yes.**

Repro: fit a `CatBoostClassifier(loss_function="MultiClass")` on a 3-class
synthetic set, then call `model.get_object_importance(test_pool, train_pool,
top_size=3)`.

```
fit ok, classes_: [0 1 2]
get_object_importance FAILED: CatBoostError catboost/private/libs/documents_importance/ders_helpers.cpp:95: Error function MultiClass is not supported yet in ostr mode
```

Full traceback bottoms out in `_catboost.pyx` (compiled extension) →
`ders_helpers.cpp:95`.

**Root cause.** `catboost/private/libs/documents_importance/ders_helpers.cpp`,
function `GetEvaluateDerivativesFunc(ELossFunction lossFunction)`, is a
hardcoded `switch` allowlisting only scalar (single-derivative) losses:

```cpp
static TEvaluateDerivativesFunc GetEvaluateDerivativesFunc(ELossFunction lossFunction) {
    switch (lossFunction) {
        case ELossFunction::Logloss:
        case ELossFunction::CrossEntropy:
            return EvaluateDerivativesForError<TCrossEntropyError>;
        case ELossFunction::RMSE:
            return EvaluateDerivativesForError<TRMSEError>;
        case ELossFunction::MAE:
        case ELossFunction::Quantile:
            return EvaluateDerivativesForError<TQuantileError>;
        case ELossFunction::Expectile:
            return EvaluateDerivativesForError<TExpectileError>;
        case ELossFunction::LogLinQuantile:
            return EvaluateDerivativesForError<TLogLinQuantileError>;
        case ELossFunction::MAPE:
            return EvaluateDerivativesForError<TMAPError>;
        case ELossFunction::Poisson:
            return EvaluateDerivativesForError<TPoissonError>;
        default:
            CB_ENSURE(false, "Error function " + ToString(lossFunction) + " is not supported yet in ostr mode");  // line 95
    }
}
```

`MultiClass` falls into `default` and hits the `CB_ENSURE`. This isn't a
version-specific regression: the whole `ostr` (object-strength/leaf-influence)
mechanism is built around a single scalar approx per document
(`TVector<double> approxes`, one first/second/third-derivative vector — see
`EvaluateDerivativesForError<TError>` in the same file) and was never
generalized to the per-class approx vector that `MultiClass` produces. This
matches upstream issue #869's description exactly.

**Confidence: 95.** Exact traceback line matches the exact `CB_ENSURE` call
site quoted above; the `switch`'s exhaustive allowlist (no `MultiClass` case,
no generic fallback) is unambiguous, structural evidence of "not implemented
yet," not an incidental bug. Docked from 100 only because the src-copy used
for cross-reference is a separate checkout, not `vendor/catboost/` inside
this worktree (version string matches `1.2.10`, but it wasn't rebuilt from
that exact checkout to bit-for-bit confirm the same binary).

## Finding 2: multi-target losses (`MultiRMSE`, `MultiLogloss`)

**Reproduced: partially, with a materially different result than the spec's
phrasing implies.**

Repro: build `Pool`s with matrix-shaped labels (`(30, 3)`), fit, predict,
then call `get_object_importance`, for both losses (`CatBoostRegressor` for
`MultiRMSE`, `CatBoostClassifier` for `MultiLogloss` — the regressor rejects
`MultiLogloss` outright: `_check_is_compatible_loss` raises `CatBoostError:
Invalid loss_function='MultiLogloss': for regressor use RMSE, MultiRMSE, ...`).

Actual output:

```
==================== MultiRMSE ====================
Pool construction with matrix-shaped label: OK, label shape (30, 3)
fit OK
predict OK, shape (5, 3)
get_object_importance FAILED: CatBoostError catboost/libs/data/target.h:316: Attempt to use multi-dimensional target as one-dimensional
==================== MultiLogloss ====================
Pool construction with matrix-shaped label: OK, label shape (30, 3)
fit OK
predict OK, shape (5, 3)
get_object_importance FAILED: CatBoostError catboost/libs/data/target.h:316: Attempt to use multi-dimensional target as one-dimensional
```

**Which step is actually "unusable":** neither `Pool` construction, `fit`,
nor `predict` fail for either loss — the spec's own phrasing ("pool path
does accept matrix labels") is confirmed correct. The **only** broken API
is `get_object_importance` — the exact same entry point as Finding 1, not a
separate multi-target-specific failure elsewhere in the fit/predict path.
The spec's "reported unusable" claim, read plainly, would suggest a broader
breakage (e.g. training itself); that is not what reproduces.

**Root cause.** Same subsystem as Finding 1, one call earlier in the chain.
`catboost/private/libs/documents_importance/tree_statistics.cpp`,
`ITreeStatisticsEvaluator::EvaluateTreeStatistics`, calls:

```cpp
EvaluateDerivatives(
    lossFunction,
    leafEstimationMethod,
    localApproxes,
    *processedData.TargetData->GetOneDimensionalTarget(),   // <-- throws first
    &FirstDerivatives,
    &SecondDerivatives,
    &ThirdDerivatives
);
```

`GetOneDimensionalTarget()` (`catboost/libs/data/target.h:316`) is:

```cpp
TMaybeData<TConstArrayRef<float>> GetOneDimensionalTarget(const TString& name = "") const {
    const auto target = GetTarget(name);
    if (target) {
        CB_ENSURE(target->size() == 1, "Attempt to use multi-dimensional target as one-dimensional");  // line 316
        return target.GetRef()[0];
    }
    ...
}
```

Because `MultiRMSE`/`MultiLogloss` targets are genuinely multi-dimensional
(`target->size() == 3` here), this `CB_ENSURE` fires as the argument to
`EvaluateDerivatives` is evaluated — **before** the loss-function `switch`
in Finding 1 is even reached. `MultiClass`'s target, by contrast, stays
one-dimensional (a class-index column), so it passes this check and fails
one level deeper, at the `switch`'s `default` case instead. Both failures
are the same architectural gap (the `ostr`/object-importance machinery is
hardcoded to a single scalar target/approx per document) surfacing at two
different checkpoints depending on whether the loss's target tensor itself
is multi-dimensional (`MultiRMSE`/`MultiLogloss`, caught at
`GetOneDimensionalTarget`) or only its approx is (`MultiClass`, caught one
call later at the loss-function `switch`).

**Confidence: 92.** Exact traceback line matches the exact `CB_ENSURE` call
site quoted above, and the call graph (`EvaluateTreeStatistics` →
`GetOneDimensionalTarget` as an eagerly-evaluated argument) directly explains
why the failure point differs from Finding 1 despite being the same root
mechanism. Slightly lower than Finding 1 because `fit`/`predict` succeeding
was determined empirically (the spec didn't specify which step breaks), and
because `MultiLogloss` required using `CatBoostClassifier` instead of
`CatBoostRegressor` (undocumented in the ticket) to get past `fit` at all —
a minor interpretation call, not a source-level ambiguity.
