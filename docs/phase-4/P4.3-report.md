# P4.3: plot_tree parity (catboost-8z4.52)

## What was implemented

`catboost.plot_tree(model, tree_idx, pool = NULL)` (`R/catboost.R`), exported and documented
(`man/catboost.plot_tree.Rd`, roxygen2-generated).

Python's `CatBoost.plot_tree` returns a `graphviz.Digraph` built from the model's own
per-tree splits and leaf values (`catboost/python-package/catboost/core.py`
`_get_tree_splits`/`_get_tree_leaf_values`, reading the vendor `TFullModel` tree layout).
`catboost.plot_tree` reuses `catboost.save_model(model, tmp, file_format = "json", pool =
pool)` — an **existing** entry point, no new native C++ glue was added — to read the exact
same split/leaf data (the JSON exporter serializes the same `TObliviousTrees` layout Python's
tree-print routine reads), then reconstructs the DOT-text graph with base R string building.

No new package dependency was added (`DESCRIPTION`'s `Imports: jsonlite` already covers the
JSON parsing needed; no `DiagrammeR`/graphviz R binding is used anywhere in the codebase and
none was required — the differential-test target per spec §4.3's "Structural" row is the
canonical node/edge JSON, not a rendered image, and the "object of the expected class" smoke
test only needs an S3 class, not a real graph object).

Return value: an object of class `catboost.plot_tree`, a list with:
- `dot` — character scalar, DOT-language source text (assembled from the same node/edge data,
  not used by the tests as a comparison target, only as the "renderable" artifact).
- `nodes` — `data.frame(id, label, color, shape)`.
- `edges` — `data.frame(from, to, label)`.

Scope: only oblivious (symmetric) trees with `FloatFeature`/`OneHotFeature` splits are
supported. Any other split type (e.g. `OnlineCtr`), or a non-oblivious tree
(`catboost._is_oblivious(model)` false / no `oblivious_trees` key in the JSON export), stops
with an explicit R error rather than silently mis-rendering. `tree_idx` out-of-range and
multi-dimensional leaf values (multiclass models) are also rejected explicitly rather than
producing wrong output — the fixture/tests only exercise single-dimension (binary
classification) leaves, matching the two Task 1/2 precedent fixtures' scope.

Node/edge assembly mirrors Python's own `_plot_oblivious_tree` layer-by-layer node
numbering (root = layer 0, doubling layer sizes per depth, leaves last; node ids assigned
by a running counter across all layers; edges labelled `No`/`Yes` for the left/right
child) — verified empirically against the real Python object's `graphviz.Digraph.body`
entries (see fixture generator), not re-derived from documentation.

### Categorical (one-hot) split value decoding — inherited R-infra limitation

Confirmed at the vendor level (`quantized_pool_analysis.cpp:GetCatFeatureValues`, read-only,
not modified): it reads `dataset.ObjectsData->GetCatFeaturesHashToString(...)`, a
hash-to-string dictionary that is **never populated** for a Pool built by
`catboost.load_pool`/`catboost.from_matrix`, because those R entry points pre-hash
categorical columns into floats via `CatBoostHashStrings_R` before the value ever reaches the
vendor pool builder — the original strings are gone by the time the C++ pool object exists.
This is the exact same root cause `catboost.calc_feature_statistics` (P4.1) already hit and
documented in `test_calc_feature_statistics.R`'s header comment (confidence 95 — read
directly, not inferred).

Task 1 worked around it with an explicit `cat_feature_values` override parameter. Task 3's
brief pins the signature to exactly `catboost.plot_tree(model, tree_idx, pool = NULL)` — no
override parameter — so `catboost.plot_tree` instead:
1. Tries the same native calls `calc_feature_statistics` uses
   (`CatBoostGetCatFeatureValues_R` for candidate strings from the pool,
   `CatBoostCalcCatFeaturePerfectHash_R` to re-hash each candidate with the model's own
   perfect-hash function until the split's hash is matched).
2. When the pool has no candidate strings to offer (the common case for any R-built Pool),
   falls back to a deterministic `"<hash:...>"` label instead of hard-failing the whole plot
   or silently mis-labelling the node.

This is flagged as **inherited, not new** technical debt (confidence 90 — same documented
root cause, not independently re-verified beyond confirming the vendor source and
reproducing the empty-candidates behavior locally). Fixing it properly would mean
re-architecting `catboost.from_matrix`'s categorical-column ingestion to preserve a
hash-to-string dictionary across the whole package — far outside a single "add plot_tree"
task's blast radius, and forbidden by the "minimal necessary changes" directive.

## Test

`tests/testthat/test_plot_tree.R`, differential test against a pinned Python 1.2.10 oracle
fixture (`tests/fixtures/oracle/plot_tree.json`, generated by
`tools/oracle/gen_plot_tree_fixture.py`). The fixture is built by regex-parsing the **real**
`graphviz.Digraph.body` entries the real Python `plot_tree()` call produces (one list item
per `node()`/`edge()` call — a single source of truth, not a reimplementation of
`_plot_oblivious_tree`'s algorithm), so the oracle is exactly what a user would see from
Python, canonicalized to plain node/edge JSON per spec §4.3.

Three model/pool combinations, matching structurally:
- Float-only tree (depth 3, 2 float features), **with** pool: exact node/edge match
  (id/label/color/shape, from/to/label), including exact `%.6g`-formatted split borders and
  `%.3f`-formatted leaf values.
- Same float-only tree, **without** pool: exact match, verifying the flat-feature-index
  fallback (`"1, value>1.05"` style) instead of names — mirrors Python's own `pool = NULL`
  fallback exactly (empirically confirmed against the real Python object first).
- Categorical (one-hot) tree, with pool: exact match on ids/edges/colors/shapes and on the
  float-feature label; the one-hot value token is normalized away before comparison (see
  "inherited limitation" above) and separately asserted to match the documented
  `", value=<hash:...>"` fallback shape.

Plus 4 negative-path tests: non-model, non-pool, out-of-range `tree_idx`, and a categorical
split with no pool raising the same parity error message Python's own `CB_ENSURE` uses
("training dataset is required if categorical features are present in the model").

## Concerns / confidence notes

- **Categorical value fallback (confidence 90)**: as documented above — inherited, not new,
  R-infra limitation. A future task could fix this properly by teaching
  `catboost.from_matrix`'s cat-column ingestion to retain a hash→string dictionary in the
  vendor pool object, which would let both `catboost.calc_feature_statistics` and
  `catboost.plot_tree` drop their respective fallback paths. Filing that as a separate,
  explicit follow-up ticket rather than bundling it here is a deliberate scope decision, not
  an oversight — Task 3's brief pins a 3-argument signature that has no room for
  `calc_feature_statistics`'s `cat_feature_values` override, and the correct fix is a Pool
  ingestion change with a much larger blast radius than a single new function.
- **Border/leaf-value formatting (confidence 95)**: `%.6g`/`%.3f` were reverse-engineered
  empirically from the real Python `plot_tree()` output across several non-round border
  values (`2.91667`, `4.93889`, `1.05556` — all 6-significant-digit `%g`), not read from the
  vendor C++ print routine's source (not present in this worktree's read-only vendor
  checkout at task start; confirmed present in the main checkout's `vendor/catboost`, but the
  empirical match across multiple values is strong enough evidence I did not additionally
  grep the C++ source for the exact format string).
- **Multiclass / non-oblivious trees**: explicitly out of scope (loud error, not silent wrong
  output) — matches Task 1/2's established practice of pinning simple single-dimension
  fixtures and erroring rather than guessing on unexercised shapes.

## Fix round 1 (task review finding)

**Finding (Important):** `resolve_cat_value()`'s hash-fallback formatter used
`sprintf("<hash:%d>", as.integer(target_hash))`. `target_hash` is a vendor `ui32`
(`OneHotFeature.Value`, range up to ~4.29e9) surfaced as an R `double`. `as.integer()`'s
ceiling is `.Machine$integer.max` (2147483647) — any hash above that silently becomes `NA`,
collapsing every out-of-range hash to the identical `"<hash:NA>"` label instead of a distinct
fallback string.

**Fix:** Extracted the formatter into a small non-exported helper,
`catboost.plot_tree.format_hash_fallback(target_hash)` (`R/catboost.R`), using
`sprintf("<hash:%.0f>", target_hash)` — R doubles are exact integers up to 2^53, well past the
`ui32` range, so `%.0f` never truncates or rounds a real hash value. `%d` (`as.integer()`)
required a coercion `%.0f` on a double does not.

**Test:** `tests/testthat/test_plot_tree.R` — new `test_that` constructs a synthetic
out-of-range hash (`3000000000`, > `.Machine$integer.max`, exact as a double) directly against
the extracted helper, rather than relying on a fitted model happening to produce a
sufficiently large hash. Asserts the exact formatted string and that no `"NA"` appears in it.
