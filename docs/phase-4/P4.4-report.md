# catboost-8z4.53 (P4.4) — `ShapInteractionValues` / `PredictionDiff` argument-value parity

Task: extend `catboost.get_feature_importance`'s existing `type`/`fstr_type` argument
(`R/catboost.R:3130`) to accept `"ShapInteractionValues"` and `"PredictionDiff"` as
values, per spec §4.2 (enum member → accepted value of an existing argument, not a
new export).

## Step 1 — Existing accepted values

Before this change, `catboost.get_feature_importance`'s output-dispatch `if`/`else if`
chain (R/catboost.R, tail of the function) accepted:
`"Interaction"`, `"ShapValues"`, `"PredictionValuesChange"`, `"FeatureImportance"`,
`"LossFunctionChange"`, else `stop("Unknown type: ", type)`. The native call
(`.Call("CatBoostCalcRegularFeatureEffect_R", ...)`) ran unconditionally before that
dispatch, so passing `type = "ShapInteractionValues"` or `"PredictionDiff"` previously
reached the C++ layer and failed there (see Step 3).

## Step 2 — Python oracle introspection

`get_feature_importance()` docstring and body
(`catboost/python-package/catboost/core.py:3385-3600`, vendor pin):

- `data : ... If type == 'PredictionDiff' data must contain a matrix of feature values
  of shape (2, n_features).` (line 3401) — confirmed in code at line 3531-3534:
  `if type == EFstrType.PredictionDiff: data, _ = self._process_predict_input_data(...);
  if data.num_row() != 2: raise CatBoostError("{} requires a pair of documents, found {}"...)`.
  **A single pool with exactly 2 rows — no second/reference pool argument.** The
  `reference_data` parameter exists on `get_feature_importance` but is documented
  "used only for 'ShapValues' type" (line 3472-3474) and is not referenced in the
  `PredictionDiff` branch.
- ShapInteractionValues: `data must be of Pool type` (line 3395), routes to
  `CalcShapFeatureInteractionMulti(...)` in `_calc_fstr` (`_catboost.pyx:5714`), also
  single-pool, no reference pool. Return shape documented as
  `(n_objects, n_features + 1, n_features + 1)`, or with a leading class axis for
  multiclass (line 3504-3507).

Confidence: 100 (direct source quotes, vendor-pinned `catboost/python-package/catboost/core.py`
and `_catboost.pyx`).

## Step 3 — Native glue gap (vendor, read-only)

`vendor/catboost/catboost/libs/fstr/calc_fstr.h` declares
`GetFeatureImportances(EFstrType type, ..., TDataProviderPtr referenceDataset, ...)`
(the function `src/catboostr.cpp:CatBoostCalcRegularFeatureEffect_R` already calls).
Its `.cpp` switch (`calc_fstr.cpp:491-547`) has a case for `EFstrType::PredictionDiff`
(`return GetPredictionDiff(model, *dataset, &localExecutor);`, using the existing
`dataset` argument, not `referenceDataset`) but **no case for
`EFstrType::ShapInteractionValues`** — falls to `default: CB_ENSURE(false, "Unexpected
Fstr type")`, an unrecoverable native abort. `GetPredictionDiff`
(`compare_documents.cpp:251-262`) confirms the 2-row pairing (`predict[idx] -
predict[idx ^ 1]`, `compare_documents.cpp:230`).

Conclusion: `PredictionDiff` was **already fully wired** through the existing native
entry point and needed only R-side dispatch/validation. `ShapInteractionValues`
needed new native plumbing, routed through the already-declared (and already
`#include`d via `calc_fstr.h`) `CalcShapFeatureInteractionMulti`
(`calc_fstr.h:143-152`), which returns `TVector<TVector<TVector<TVector<double>>>>`
(`[featureIdx1][featureIdx2][dim][documentIdx]`, per `shap_interaction_values.h:22-23`).

Confidence: 100 (direct code quotes from vendor pin; zero writes made under
`vendor/catboost/`).

## Fix round 1 (task review finding)

**Finding (test gap):** `tests/testthat/test_fstr_shap_prediction_diff.R` did real float
comparisons (tolerance `1e-6`) against the pinned Python-oracle fixture, but the fixture
model was Logloss binary classification (`model->GetDimensionsCount() == 1`), so only the
non-multiclass 3D branch of the new `src/catboostr.cpp` `ShapInteractionValues` code
(`CatBoostCalcRegularFeatureEffect_R`) was exercised. The 4-nested-loop `if (multiClass)`
branch — which reorders `fstr[f1][f2][dim][doc]` into
`ptr_result[doc + docCount * (dim + approxDimension * (f1 + featuresCount * f2))]`, one
extra `dim` axis versus the non-multiclass path — was completely untested, even though the
extra axis is exactly the kind of place an axis-order bug hides.

**Fix:** Extended `tools/oracle/gen_fstr_shap_prediction_diff_fixture.py` to also train a
3-class `MultiClass` model (`MULTICLASS_LABEL = [i % 3 for i in range(N_ROWS)]`, same
`num1`/`num2` features and rows as the existing binary model) and pin its
`get_feature_importance(type="ShapInteractionValues")` output as
`expected.multiclass_shap_interaction_values` (shape `(5, 3, 3, 3)` =
`(doc, dim, f1, f2)`) in `tests/fixtures/oracle/fstr_shap_prediction_diff.json`. Added a
new `test_that("get_feature_importance: ShapInteractionValues matches Python oracle
(MultiClass)")` in `tests/testthat/test_fstr_shap_prediction_diff.R`, reusing the same
`shap_pool` (first 5 rows) against a freshly trained `MultiClass` model, comparing both
`dim()` and numeric values (tolerance `1e-6`) to the new fixture field. No `src/catboostr.cpp`
change — the multiclass branch was already implemented in the original commit, only
test-covered here.
