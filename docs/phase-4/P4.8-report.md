# catboost-8z4.57 (P4.8) — CLI `model-based-eval` mode parity (`catboost.model_based_eval`)

Task: make the CLI's `model-based-eval` mode reachable from R, verified by a differential
test against a pinned CLI oracle. Parity-matrix row
(`tests/fixtures/parity/matrix.dispositioned.json`):

- `mode:model-based-eval` — oracle `cli`, kind `mode`, disposition `method_mode_shaped`,
  method `elementwise`, tolerance `1e-9`, was `state: red`, `test_id: null`.

**Headline result: the R function is implemented in process, but the differential
comparison is blocked and the matrix row stays red.** The mode is GPU-only and no CUDA
device exists on this host — neither side of the comparison can produce a number. This is
the "blocking design gap reported, not silently skipped" branch of the ticket's Definition
of Done. Details in Step 3 and Step 6.

## Step 3 — The blocking finding: this mode is GPU-only

`model-based-eval` cannot run on CPU. Three independent gates, quoted:

1. **The CLI mode itself asserts GPU.** `vendor/catboost/catboost/app/mode_model_based_eval.cpp:40`:

   ```cpp
   CB_ENSURE(NCatboostOptions::GetTaskType(catBoostJsonOptions) == ETaskType::GPU);
   ```

2. **The option parser only recognises the mode's options under GPU.**
   `catboost/private/libs/options/plain_options_helper.cpp:393-404`:

   ```cpp
   //feature evaluation options
   if (GetTaskType(plainOptions) == ETaskType::GPU) {
       auto& modelBasedEvalOptions = trainOptions["model_based_eval_options"];
       ...
       CopyOption(plainOptions, "features_to_evaluate", &modelBasedEvalOptions, &seenKeys);
   ```

3. **The CPU trainer refuses the operation outright.**
   `catboost/libs/train_lib/train_model.cpp:936-943`:

   ```cpp
   void ModelBasedEval(...) const override {
       CB_ENSURE(false, "Model based eval is not implemented for CPU");
   }
   ```

Reproduced against the pinned binary, both branches. With the default (CPU) task type the
option parser rejects the mode's own flag:

```
$ ./tools/oracle/cli/bin/catboost-v1.2.10 model-based-eval \
    --learn-set smoke_data.csv --column-description smoke.cd --delimiter , --has-header \
    -t smoke_data.csv --features-to-evaluate 0 --loss-function Logloss -i 10 \
    --train-dir mbe_try
(TCatBoostException) catboost/private/libs/options/plain_options_helper.cpp:512: Unknown option {features_to_evaluate} with value "[[0]]"
EXIT=1
```

With `--task-type GPU` it gets as far as the CUDA runtime and dies there:

```
$ ./tools/oracle/cli/bin/catboost-v1.2.10 model-based-eval ... --task-type GPU
(TCudaException) catboost/cuda/cuda_lib/cuda_base.h:265: CUDA error 35: CUDA driver version is insufficient for CUDA runtime version
EXIT=1
```

This is the situation §9.1 of the design spec already records: "CatBoost's GPU backend is
CUDA-only. The development machine has an AMD GPU, so no CatBoost GPU execution is possible
locally." **The pinned CLI oracle cannot produce a `model-based-eval` fixture on this
hardware.** There is nothing to compare against, at any tolerance. §4.4 forbids counting a
skipped test green, so `mode:model-based-eval` cannot be flipped green by this ticket, and
was not.

Phase 4's scope line in the spec (§5, line 638) lists "the CLI's `eval-feature`, `roc`,
`model-based-eval` modes" together. That grouping was written before anyone checked which
of the three are GPU-only; `eval-feature` (P4.7) and `roc` (P4.6) are not, this one is. The
verification half of this row belongs to Phase 7, alongside the rest of the GPU parity
decision in §9.1.

Confidence: 100 (source quotes plus two reproduced runs of the pinned binary).

## Step 4 — Design decision: in process, not a subprocess wrapper

Following P4.7's methodology, the question is whether the CLI mode is a thin driver over a
core function already linked into `libcatboostr.so`. It is:

- `mode_model_based_eval.cpp` parses flags, converts feature names to indices, applies
  three guards, and then calls one core function:

  ```cpp
  ModelBasedEval(poolLoadParams, outputOptions, catBoostJsonOptions);
  ```

- That overload is declared in `catboost/libs/train_lib/train_model.h:147` and built from
  `catboost/libs/train_lib/train_model.cpp`, a source of `catboost-libs-train_lib`.
- `catboost-libs-train_lib` is **already** linked into the `catboostr` target
  (`src/CMakeLists.txt`), for `CrossValidate` and `EvaluateFeatures`. `private-libs-app_helpers`
  is **also** already linked (P3.3's dataset-statistics work), which supplies `InitOptions`
  and `CopyIgnoredFeaturesToPoolParams`.

So the in-process route adds **no new link dependency and no CMake change**. Decision:
**in process**, same as P4.7 and P3.3.

The rejected alternative, recorded rather than silently skipped: a subprocess wrapper around
the pinned CLI binary would need a 287 MB gitignored binary present at runtime, pay process
spawn plus dataset re-read per call, and require temp-file, cleanup and stderr-propagation
code — and it would still fail on this host for exactly the same CUDA reason, so it buys
nothing even on the verification axis.

### One material difference from P4.7: this entry point is file-driven

`EvaluateFeatures` (P4.7) accepts an in-memory `TDataProviderPtr`, so `catboost.eval_feature`
takes a `catboost.Pool`. `ModelBasedEval` does not. The only **public** overload takes
`NCatboostOptions::TPoolLoadParams` — i.e. dataset file paths. The in-memory-capable
overload at `train_model.cpp:1421` is `static` and therefore not linkable, and duplicating
its body in this package would be reimplementing vendor code.

A file-oriented R API is also the faithful one here regardless of linkage: the mode reads
the baseline model's training snapshot from disk (`--baseline-model-snapshot`) and writes
its results as per-experiment error logs into `train_dir`. There is no in-memory summary
object to return, unlike `eval-feature`'s `TFeatureEvaluationSummary`.

So `catboost.model_based_eval()` takes `learn_set` / `test_set` / `column_description`
paths, mirroring the CLI, and returns the `train_dir` invisibly. This deviation from
`catboost.eval_feature`'s pool-first convention is deliberate and documented in the
function's roxygen block.

### All six mode-specific flags are plain-JSON option keys

Unlike `eval-feature` (whose options live in a separate `TFeatureEvalOptions` struct that
must be built by hand), every `model-based-eval` flag is copied straight from plain JSON by
`PlainJsonToOptions` (quoted in Step 3). The R wrapper therefore merges its six named
arguments into the `params` list and the native side does no per-option `SEXP` handling at
all. That is why `CatBoostModelBasedEval_R` takes six arguments rather than twelve.

## Step 5 — Implementation

**Native (`src/catboostr.cpp`, `src/catboostr.h`, `src/init.c`, `src/catboostr.exports`).**
`CatBoostModelBasedEval_R(fitParamsAsJson, learnSetPath, testSetPath, cdPath, delimiter,
hasHeader)` transcribes `mode_model_based_eval.cpp:26-52` with the command-line parsing
replaced by arguments: build `TPoolLoadParams`; `InitOptions("")`;
`ConvertIgnoredFeaturesFromStringToIndices`; `ConvertFeaturesToEvaluateFromStringToIndices`;
`PlainJsonToOptions`; `ConvertParamsToCanonicalFormat`; `CopyIgnoredFeaturesToPoolParams`;
load `TOutputFilesOptions`; apply the CLI's guards; force `metric_period` to 1; call
`ModelBasedEval`.

Two deliberate deviations, both documented in the code:

1. **The GPU check runs against the flat options, before `PlainJsonToOptions`.** The CLI's
   check at line 40 fires *after*, so on a CPU task type the CLI never reaches it and dies
   in the option parser with `Unknown option {features_to_evaluate}` instead (reproduced in
   Step 3). Checking first reaches the identical verdict one step earlier and yields the
   specific, tested error §4.4 requires of a GPU-only capability. The CLI's `CB_ENSURE` has
   no message at all; ours says
   `Model based eval is not implemented for CPU: params must set task_type = "GPU"`.
2. `LoadPoolMetaInfoOptions` (`mode_model_based_eval.cpp:30`) is skipped, because
   `--pool-metainfo-path` is not exposed by this R function, making it a no-op.

**R (`R/catboost.R`).** `catboost.model_based_eval(learn_set, test_set,
features_to_evaluate, baseline_model_snapshot = "baseline_model_snapshot",
column_description = NULL, params = list(task_type = "GPU"), offset = 1000,
experiment_count = 200, experiment_size = 5,
use_evaluated_features_in_baseline_model = FALSE, delimiter = "\t", has_header = FALSE)`.
Naming follows §4.2's `verb_object` snake_case rule, never a dotted name. Defaults are the
C++ `TModelBasedEvalOptions` constructor defaults
(`catboost/private/libs/options/model_based_eval_options.cpp`).

`features_to_evaluate` is a single string in the CLI's own
`--features-to-evaluate` syntax (`"0,3-5;7"`, names, `#tag` references), because that is
literally the type the plain option holds: `ConvertFeaturesToEvaluateFromStringToIndices`
(`feature_names_converter.cpp:219`) reads `.GetString()` and writes back a
`TVector<TVector<int>>`. Passing a string means R gets name, range and tag resolution for
free, identically to the CLI, with zero conversion code.

R-side validation added ahead of any dataset read: path existence, non-empty single-string
`features_to_evaluate`, and `experiment_count * experiment_size <= offset`
(`TModelBasedEvalOptions::Validate()`).

**No new fixture.** `gen_eval_feature_fixture.sh` has no counterpart here because the
oracle run cannot be executed (Step 3). Committing a hand-written or invented fixture would
be worse than none.

## Step 6 — Tolerance and what is actually verified

The row's declared tolerance stays at §4.3's CLI default, relative `1e-9`, never bit-exact —
not an override, so no first-principles override justification is required. It is
**unexercised**: no numeric comparison against the CLI exists, because no CLI output exists.
No test in `tests/testthat/test_model_based_eval.R` asserts a float against the CLI.

What *is* verified without CUDA is more than it first appears. `ModelBasedEval`
(`train_model.cpp:1533`) loads the datasets, runs `ValidateFeaturesToEvaluate`
(`train_model.cpp:1413`) against the real pool, and builds the quantized feature info
**before** the GPU learning library is ever requested (`train_model.cpp:1439`). So reaching
that GPU error is proof that the entire chain the R wrapper is responsible for executed
correctly: plain-JSON option mapping, feature-name/range/tag resolution, ignored-feature
conversion, column description, delimiter and header handling, output options. The tests
assert exactly that, by message:

- CPU task type (explicit and by omission) → `Model based eval is not implemented for CPU`.
- GPU requested, no CUDA → `Can't load GPU learning library. Module was not compiled or
  driver is incompatible with package.` — a specific error, never a silent CPU fallback.
  On a CUDA host this test takes the other branch and skips with a pointer to this report.
- `features_to_evaluate = "99"` → `Feature index 99 is too large; dataset has only 3
  features` (proves the datasets were loaded from the given paths with the given cd file,
  delimiter and header).
- `features_to_evaluate = "cat1"` (the only named feature in `smoke.cd`) resolves and
  reaches the GPU check; `"nosuch"` → `String 'nosuch' is not a feature name`.
- Tested feature also ignored, by index and by name → `Error: feature N is ignored`
  (`mode_model_based_eval.cpp:47-50`), with a negative control that ignoring an untested
  feature runs through to the GPU check.
- Argument validation: missing files, empty/multi-element `features_to_evaluate`,
  `offset < experiment_count * experiment_size`.
- One explicit `skip()` naming the blocker, so the gap appears in every test run and cannot
  be mistaken for green.
