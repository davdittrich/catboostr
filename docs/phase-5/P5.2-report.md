# P5.2: grid_search / randomized_search — catboost-8z4.59

## 1. Python oracle behavior (quoted)

`catboost/python-package/catboost/core.py:4415` (`CatBoost.grid_search`) and
`:4522` (`CatBoost.randomized_search`) both delegate to a shared private method,
`core.py:4340` `CatBoost._tune_hyperparams`:

```python
return self._tune_hyperparams(
    param_grid=param_grid, X=X, y=y, cv=cv, n_iter=-1,
    ...
)
```
(`grid_search`; `randomized_search` calls the same method with `n_iter=n_iter`,
a positive int, instead of the `-1` sentinel.)

`_tune_hyperparams` (`core.py:4403`) calls `self._object._tune_hyperparams(...)`,
a Cython `cpdef` (`_catboost.pyx:5933-6001`):

```cython
if n_iter == -1:
    GridSearch(
        prep_grids.tree, prep_params.tree, ttParams, cvParams,
        prep_params.customObjectiveDescriptor, prep_params.customMetricDescriptor,
        train_pool.__pool, &results, &trainTestResults,
        choose_by_train_test_split, return_cv_results, verbose
    )
else:
    RandomizedSearch(
        n_iter, prep_grids.custom_rnd_dist_gens, prep_grids.tree, prep_params.tree,
        ttParams, cvParams, prep_params.customObjectiveDescriptor,
        prep_params.customMetricDescriptor, train_pool.__pool, &results,
        &trainTestResults, choose_by_train_test_split, return_cv_results, verbose
    )
```

`GridSearch`/`RandomizedSearch` are native C++ free functions
(`catboost/private/libs/hyperparameter_tuning/hyperparameter_tuning.h`), **not** a
Python-side loop over `fit`/`cv`. This contradicts the ticket's Reference Data
assumption ("Python's grid_search/randomized_search internally repeat
fit/cv... R already has catboost.train/catboost.cv; this ticket wraps them in a
search loop, it does not add new native training paths") — that assumption does
not hold once the actual Cython source is read. The Constraints section's own
escape hatch ("no new native entry points unless the Python implementation
itself requires one you can point to in its source") is what applies here, and
is exercised below.

Return-value shape (`_catboost.pyx:6009-6030`, both branches share it):
```python
cv_results = defaultdict(list)  # per-metric test/train-<metric>-mean/std lists
...
best_params = json_value_to_dict(results.BestParams)
return {'params': best_params, 'cv_results': cv_results}
```

`hyperparameter_tuning.h` signatures actually called:
```cpp
void GridSearch(const NJson::TJsonValue& gridJsonValues, const NJson::TJsonValue& modelJsonParams,
    const TTrainTestSplitParams& trainTestSplitParams, const TCrossValidationParams& cvParams,
    const TMaybe<TCustomObjectiveDescriptor>&, const TMaybe<TCustomMetricDescriptor>&,
    TDataProviderPtr data, TBestOptionValuesWithCvResult* bestOptionValuesWithCvResult,
    TMetricsAndTimeLeftHistory* trainTestResult, bool isSearchUsingTrainTestSplit,
    bool returnCvStat, int verbose);
void RandomizedSearch(ui32 numberOfTries, const THashMap<TString, TCustomRandomDistributionGenerator>&,
    /* same remaining params as GridSearch */);
```
`TBestOptionValuesWithCvResult { TVector<TCVResult> CvResult; NJson::TJsonValue BestParams; }`
— the exact same `TCVResult` shape `CatBoostCV_R` already converts to an R
`data.frame`.

Two algorithm details that matter for bit-exactness, both confirmed by reading
`hyperparameter_tuning.cpp`:
- The train/test split used *during* the search is never stratified regardless
  of the `stratified` argument (`ttParams.Stratified = False` is hardcoded in
  `core.py:4404` area); `stratified` only reaches `cvParams` (used for the
  post-search CV statistics on the winning candidate).
- `RandomizedSearch`'s combination sampler (`TRandomizedProductIterator`) uses
  `TRandom random;` — `cpu_random.h:8`'s default constructor seeds with `0`, a
  fixed constant, not tied to `partition_random_seed`. So which parameter
  combinations get sampled (not just which one wins) is deterministic and
  reproducible given the same grid and `n_iter`.

## 2. What was implemented

Given the native-call finding above, R's `catboost.grid_search` /
`catboost.randomized_search` call the exact same `NCB::GridSearch` /
`NCB::RandomizedSearch` C++ entry points Python calls, rather than
approximating the search with an R-side loop over `catboost.cv`. This is the
only way to match best-params/`cv_results` at the spec's default `1e-12`
tolerance: the grid/quantization-parameter enumeration order and train/test
split reuse live entirely in that native code, and are infeasible to
replicate independently from R with bit-exact fidelity.

- `src/catboostr.h` / `src/catboostr.cpp`: two new native entry points,
  `CatBoostGridSearch_R` and `CatBoostRandomizedSearch_R`, following the same
  `TPoolPtr`/`LoadFitParams`/`R_API_BEGIN`/`R_API_END` conventions every other
  function in this file already uses (e.g. `CatBoostCV_R`,
  `CatBoostEvaluateFeatures_R`). Two small shared helpers, `CVResultsToRList`
  (a `TCVResult` vector → R list, structurally identical to `CatBoostCV_R`'s
  own conversion, factored out because a third near-copy would cross the
  "abstract at 3+ occurrences" threshold) and `BestOptionValuesToRList`
  (wraps that plus the best-params JSON string into `list(params=, cv_results=)`,
  mirroring Python's own `{'params':..., 'cv_results':...}` return shape).
- `src/CMakeLists.txt`: links `private-libs-hyperparameter_tuning` (the vendor
  CMake target that builds `hyperparameter_tuning.cpp`), the same linking
  pattern P3.3/P4.1/P4.7 already established for other native entry points.
- `src/init.c` / `src/catboostr.exports`: registration for both new `.Call`
  targets.
- `R/catboost.R`: `catboost.grid_search(param_grid, pool, params = list(), cv =
  3, partition_random_seed = 0, calc_cv_statistics = TRUE,
  search_by_train_test_split = TRUE, refit = TRUE, shuffle = TRUE, stratified =
  FALSE, train_size = 0.8, verbose = TRUE)` and `catboost.randomized_search`
  (same plus `n_iter = 10`) — parameter names taken verbatim from
  `core.py:4415`/`:4522`. `param_grid`/`param_distributions` accept either a
  single named list (wrapped into a 1-element array, matching
  `core.py:4355-4356`'s `if isinstance(param_grid, Mapping): param_grid =
  [param_grid]`) or an unnamed list of named lists (multiple grids). `refit`
  reuses `catboost.train` directly (`catboost.train(pool, params =
  modifyList(params, best_params))`), matching Python's
  `self.set_params(**cv_result['params']); self.fit(X)` — this is the one part
  of the ticket's "reuse catboost.train/catboost.cv" steer that does apply
  cleanly, since R has no mutable `self` to refit in place.
- `man/catboost.grid_search.Rd` / `man/catboost.randomized_search.Rd`:
  hand-applied (roxygen2's pipeline crashes in this environment, same
  pre-existing issue P5.1 documented — reproduces unmodified on `phase-0`).
- Not implemented (explicitly out of scope, confirmed by reading
  `_PreprocessGrids.__prepare_grid`, `core.py:2080-2096`): sampling from
  `scipy.stats`-style `rvs()` distribution objects in `param_distributions`.
  R has no equivalent convention; entries must be plain value vectors, sampled
  uniformly by the native code (same as Python's own `list` branch).
  `catboost.cv`'s own `stratified` default (`FALSE`, no loss-function
  auto-detection) is kept as R's default too, documented as a deviation from
  Python's `None`-means-auto-detect in both `@param` blocks.

## 6. A real bug this caught

The first implementation of `BestOptionValuesToRList` double-`PROTECT`ed
`CVResultsToRList`'s return value (that helper already leaves its result
`PROTECT`ed for the caller, by contract/comment; the call site additionally
wrapped it in another `PROTECT(...)`). This didn't crash outright but produced
`Warning: stack imbalance in '<-'` on every call and, worse, caused the
*outer* `result` list — not the double-protected inner value — to be the one
actually popped off the protect stack by the subsequent `UNPROTECT(4)`,
leaving the real return value under-protected relative to what was intended.
Caught by the differential test run (the warning surfaced immediately) before
any incorrect-tolerance masking was needed; fixed by not re-`PROTECT`-ing an
already-protected return value. Full suite reran clean (no warnings) after the
fix.
