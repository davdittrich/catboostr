## 2. In-process-path investigation

**Finding: an in-process Python-equivalent path exists, and it needed one new
linked vendor target.** No CLI fallback, no R-side reimplementation.

Evidence chain:

1. `_catboost.pyx:6031-6055` — `_select_features` is a thin wrapper that fills a
   `TDataProviders`, reserves one eval result per test pool, and calls
   `SelectFeatures(prep_params.tree, prep_params.customMetricDescriptor,
   dataProviders, self.__model, self.__test_evals, &self.__metrics_history)`.
2. `_catboost.pyx:1263-1272` declares that symbol as
   `cdef extern from "catboost/libs/features_selection/select_features.h"
   namespace "NCB"`, i.e. the JSON-params overload
   `NJson::TJsonValue SelectFeatures(const NJson::TJsonValue& plainJsonParams, ...)`
   in `vendor/catboost/catboost/libs/features_selection/select_features.h:29-36`.
   Python calls exactly the same C++ function a C caller would.
3. That overload (`select_features.cpp:338-379`) does the option splitting itself
   (`PlainJsonToOptions` + `ConvertFeaturesForSelectFromStringToIndices`), creates
   its own `NPar::TLocalExecutor`, and calls the struct-args `SelectFeatures`
   overload. So the *only* input the caller must produce is the same plain params
   JSON `catboost.train` already builds — nothing Python-specific in between.
4. The keys are all recognised by the shared plain-options splitter:
   `plain_options_helper.cpp:494-503` copies `features_for_select`,
   `num_features_to_select`, `features_selection_steps`, `train_final_model`,
   `features_selection_algorithm`, `features_selection_grouping` and
   `shap_calc_type` into `featuresSelectOptions`.
5. **Reachability**: unlike P4.7's `EvaluateFeatures` (which lived in
   `catboost-libs-train_lib`, already linked), `SelectFeatures` lives in its own
   target `catboost-libs-features_selection`
   (`vendor/catboost/catboost/libs/features_selection/CMakeLists.linux-x86_64.txt:15`).
   It is *not* reachable transitively: that target links
   `catboost-libs-train_lib` (line 27), the dependency runs that way round, not
   back. `catboost-libs-train_lib`'s own CMakeLists does not mention
   `features_selection` at all. So one new entry in `src/CMakeLists.txt` was
   required — the same one-line addition P5.2 made for
   `private-libs-hyperparameter_tuning`. The target is configured by the
   fork's build (`catboost/libs/CMakeLists.linux-x86_64.txt:24`
   `add_subdirectory(features_selection)`), so nothing beyond the link line.

Two vendor details that shaped the implementation:

* `dstModel` must be non-null. `recursive_features_elimination.cpp:842-852`:
  when `TrainFinalModel` is set and `dstModel == nullptr`, the vendor *writes the
  final model to `result_model_file` on disk* instead of returning it. R always
  passes a real `TFullModel*` and only hands it back when `train_final_model` is
  TRUE (the one case the vendor assigns it).
* `evalResultPtrs` must be sized to the test-pool count:
  `recursive_features_elimination.cpp:708` passes it straight to `TrainModel`
  for the final fit. This mirrors Python's `self._reserve_test_evals(...)`.

### One real bug this surfaced

The first test run failed with a **~2.6e-10 relative** mismatch on
`loss_graph$loss_values` only — feature indices and the final model's
predictions already matched exactly. Root cause was not the algorithm: it was
the JSON serialisation on the way back to R. `ToString(TJsonValue)` uses the
default writer config, and `library/cpp/json/json_writer.h:16` sets
`DefaultDoubleNDigits = 10`, i.e. doubles are truncated to 10 significant
digits (`3.638...` → 2.66e-10 absolute error). Fixed at the source by writing
the summary with `NJson::WriteJson(&stream, &summaryJson, config)` where
`config.FloatToStringMode = PREC_AUTO` (shortest round-trip representation).
After that all four loss values match at 1e-12.

Note for a future ticket (out of scope here, not touched): P5.2's
`BestOptionValuesToRList` returns best params via the same
`ToString(TJsonValue)` path and therefore has the same 10-significant-digit
ceiling. It passes today because its grid values (`0.05`, `0.3`) round-trip
inside 10 digits, but a grid of longer decimals would trip it.

### Deliberate scope limits

* **Feature-tag grouping is not implemented.** Python's `grouping="ByTags"` /
  `features_tags_for_select` / `num_features_tags_to_select` select over feature
  *tags*, and an R pool cannot carry tags: `catboost.load_pool` has no
  `feature_tags` argument (Phase 3 / catboost-8z4.49 explicitly *rejects*
  `feature_tags=`). Documented in the `.Rd` rather than half-wired.
* **`plot`/`plot_file`/`log_cout`/`log_cerr` are not implemented** — Jupyter
  widget plumbing and Python stream redirection, with no R analogue (same line
  P5.2 drew for `catboost.grid_search`).
* The returned `$model` gets `create.model.base` + `tree_count` but *not*
  `catboost.train`'s full post-processing: the final model is fitted on a
  feature *subset*, so `ncol(learn_pool)` is not its feature count and feature
  importances would be indexed against the subset.
* `catboost.eval_feature` (P4.7) was neither reused nor modified. It is a
  different algorithm (scores caller-supplied feature sets by repeated CV;
  no elimination), and the two are now cross-referenced in each other's docs.

## 4. Tests

Differential test against the pinned Python oracle (catboost 1.2.10),
**tolerance 1e-12** — the spec §4.3 Python-oracle default, not an override:
R and Python call the identical native function, so nothing weaker is
justified. Feature indices and `main_indices` are compared *exactly*
(integers); only `loss_values` and the final model's predictions use the
numeric tolerance.

Fixture: 80 rows × 6 numeric features, learn = rows 1-60, eval_set = rows
61-80, `iterations=20`, `loss_function=RMSE`, `thread_count=1`,
`random_seed=0`, `steps=2`, select 3 of 6. Two arms: `RecursiveByShapValues`
with `train_final_model=TRUE`, and `RecursiveByLossFunctionChange` with
`train_final_model=FALSE`. Both oracle runs select features `[0, 3, 4]` and
eliminate `[1, 5, 2]` (elimination order preserved), with different loss
graphs.
