- `catboost.cv <- function(pool, params = list(), fold_count = 3, ...)` does **not**

  alias spellings either way).
- `catboost.grid_search`/`catboost.randomized_search` call `process_synonyms(params)`
  themselves before delegating refit to `catboost.train`.
- `catboost.select_features` calls `process_synonyms(params)` on the user's
  params, *then* appends its own extra keys (`features_for_select`,
  `num_features_to_select`, `train_final_model`, `features_selection_algorithm`,
  `features_selection_steps`, `shap_calc_type`) — these are added *after*
  validation runs, so they are correctly never checked against the 139-name set.

## 4. Generator (`tools/parity/gen_param_reference.py`)

Reads `tests/fixtures/parity/matrix.dispositioned.json`'s 139 `kind:"parameter"`
rows and, via regex over `R/catboost.R` itself (not a hand-duplicated list),
the 11 synonym groups and `catboost.load_pool`'s formal arguments. Writes,
between `# BEGIN/END GENERATED KNOWN_PARAMS` markers:

```r
.catboostr_known_params <- c(...)   # 140 names: 139 inventory names + EXTRA_KNOWN_PARAMS
```

and, between `#' % BEGIN/END GENERATED PARAM REFERENCE` markers (a `%`-prefixed
Rd-comment marker line so the block stays roxygen-contiguous but renders
invisibly), a generated `@section Full Parameter Reference (generated)`
`\describe{}` block in `catboost.train`'s roxygen doc — one `\item{name}{...}`
per canonical name, classified (via small rule tables, not per-name prose)
as: alias-of-X, Pool-construction arg, `learn_pool`/`test_pool` data arg,
dedicated-arg (`init_model`/`eval_set`), Python-only/no-R-equivalent, or
plain "native training parameter accepted in the `params` list". Idempotent
— rerun any time the inventory or synonym groups change.

`EXTRA_KNOWN_PARAMS = {"embedding_processing"}`: discovered via a full-suite
regression sweep after wiring the gate — `embedding_processing` is a
pre-existing, already-documented (catboost-8z4.45) native training param
that `test_pool_embeddings.R` already exercised successfully, but it is
absent from the 139-row machine-generated inventory (a gap in the
inventory's Python-surface scan, not in catboostr). Added to the accepted
set so the new gate cannot regress pre-existing behavior.

## 5. Validation mechanism

`validate_params_keys(params)` (R/catboost.R), called at the end of
`process_synonyms()` (covers `catboost.train`, `catboost.grid_search`,
`catboost.randomized_search`, `catboost.select_features`) and once more
directly inside `catboost.cv()` (which doesn't call `process_synonyms()`):

```r
validate_params_keys <- function(params) {
    if (isTRUE(getOption("catboostr.allow_unknown_params", FALSE))) {
        return(invisible(NULL))
    }
    unknown <- setdiff(names(params), .catboostr_known_params)
    if (length(unknown) > 0) {
        stop("Unknown catboost 'params' key(s): ", paste(unknown, collapse = ", "), ...)
    }
    invisible(NULL)
}
```

**Escape hatch:** `options(catboostr.allow_unknown_params = TRUE)` — a global
R option (not a params-list key, so it can never collide with a real
hyperparameter name and never gets serialized into the JSON sent to native
code). Chosen over a new formal argument (append-only constraint) or a
magic params-list sentinel (would need explicit stripping in every call
path before `jsonlite::toJSON`).

## 7. Findings during implementation

1. **Pre-existing bug, not fixed (out of scope), routed around**: native's
   flat `verbose` option is an **integer print-period**
   (`output_file_options.cpp: VerbosePeriod("verbose", 1)`), not a boolean.
   `params = list(verbose = FALSE)` — a pattern that looks idiomatic and
   appears nowhere pre-existing as a literal `params`-list key in this test
   suite (existing `verbose = FALSE` usages are all `catboost.grid_search`'s
   own *formal argument*, unrelated to the `params` list) — throws
   `Can't parse parameter "verbose" with value: false` at the native JSON
   layer. All new tests use `logging_level = "Silent"` instead (and the
   Python oracle fixture strips `verbose` from the exported params before
   handing them to R, since it's a purely cosmetic setting that cannot
   affect predictions). `verbose`'s own matrix row is closed via the
   alias-regression acceptance test (an integer value, not diffed
   numerically) rather than left broken.
2. Two RNG-driven stochastic training paths (Bayesian bootstrap's
   `bagging_temperature`, and Langevin boosting) produce ~1e-7-magnitude
   R-vs-Python prediction differences at identical `random_seed` — plausibly
   cross-process float non-associativity in the RNG-consuming code path, not
   a correctness bug. Both batches' tolerance widened to 1e-6 with an
   explicit `tolerance_justification` recorded in the matrix (the field
   exists precisely for this).
3. `jsonlite::toJSON(..., auto_unbox = TRUE)` collapses length-1 R vectors
   (`custom_metric = "Accuracy"` parsed back from a 1-element JSON array) to
   bare scalars instead of 1-element arrays; `test_param_family_coverage.R`
   wraps `custom_metric`/`simple_ctr`/`combinations_ctr` in `as.list()`
   before training, matching the existing `per_float_feature_quantization`/
   `ignored_features` workaround already in `prepare_train_export_parameters`.
4. The digit-truncation pitfall flagged in the task brief
   (`jsonlite::toJSON(params, digits = 10)`) was avoided by construction —
   every new fixture value has ≤10 significant digits.

## 10. Self-review / concerns

- **Judgment call, flagged per the brief's guidance**: the validation
  gate's accepted-key set is the full 139-name inventory verbatim
  (permissive), not narrowed to "only names that are real R `params` keys".
  This means e.g. `params = list(X = 1)` doesn't error even though `X` has
  no meaning as an R `params`-list key — the generated docs classify it
  ("Supplied via `learn_pool`/`test_pool`...") but the validator doesn't
  enforce that classification. Chosen deliberately: narrower validation
  risks false-positive rejections (the hard backward-compat constraint),
  and the ticket forbids restructuring `params` into a typed API.
- 12 of 138 rows (9%) are closed via the acceptance gate rather than a
  numeric oracle diff, each with a specific, checkable reason recorded in
  `tolerance_justification` (GPU-only, native-schema mismatch discovered
  during implementation, R-Pool architecture limitation already documented
  elsewhere in the suite, or a flaky/RNG-sensitive path). None are silent —
  every one is named and reasoned above.
- `catboost.cv`'s pre-existing gap (never calling `process_synonyms()`) is
  unchanged; it happens not to matter for validation correctness (see §2)
  but a user passing `eta=` to `catboost.cv` still gets a native call with
  a literal `"eta"` JSON key rather than the resolved `"learning_rate"` —
  unrelated pre-existing behavior, out of this ticket's scope.

### 11.3 Critical #2 — `used_ram_limit`'s divergence was a confound, not evidence to discard

The original report found a ~1e-7 R-vs-Python divergence in a 35-parameter
`core_training_control` batch and (wrongly) shipped by *removing*
`used_ram_limit` from the fixture rather than resolving it — exactly the
mistake the review called out. Fix: an isolated single-variable A/B fixture
batch (`used_ram_limit_isolated` vs. `used_ram_limit_baseline`, identical
params otherwise) plus a real test (`test_param_family_coverage.R`) that
checks Python-vs-Python *and* R-vs-Python at the real 1e-12 default. Result:
**bit-exact on both axes** — `used_ram_limit` was never the cause. `state:
green`, real measured evidence recorded, nothing discarded.

### 11.4 Important #6 — the actual, isolated root cause (bisection)

Same bisection method applied to the real cause: binary-searched the
35-parameter `core_training_control` batch (remove one chunk of 3-6 related
params at a time, retrain, diff against oracle) until the failing chunk was
found, then bisected that chunk key-by-key. Isolating `bagging_temperature`/
`bootstrap_type="Bayesian"` alone (the review's suspected cause, and the
original report's claimed cause) reproduces **bit-exact** (0.0 diff) — it
was never the problem. Removing exactly one other parameter,
`model_shrink_rate`, from the full batch makes the whole batch bit-exact;
removing any other single parameter does not. **`model_shrink_rate` is the
real, isolated, confirmed cause** (plausibly floating-point evaluation-order
sensitivity in the repeated multiplicative shrinkage applied across
iterations — deterministic on both sides, not associative across
implementations, not an RNG-stream difference).

Result: `core_training_control` now trains bit-exact at the real 1e-12
default (`model_shrink_mode` alone, without `model_shrink_rate`, is also
exact and stays in that batch); `bagging_temperature`/`bootstrap_type` moved
to their own small batch at the real 1e-12 default (proven exact, kept
isolated for clarity, not because it needs widening); `model_shrink_rate`
moved to its own isolated batch at a measured, justified 1e-6 (max observed
diff ~1.7e-7). The Langevin batch's widened tolerance (1e-6, ~4.2e-7
observed) was already correctly isolated (3 params only) and needed no change.
