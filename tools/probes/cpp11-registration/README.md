# cpp11 / raw `.Call` registration probe

Minimal throwaway R package that empirically settles the question spec
§4.7 depends on: **can a hand-written raw `.Call` entry point and a
cpp11-generated entry point coexist in one package's routine table,
under upstream catboostr's exact constraints** — shared-object name
(`libprobe`) different from the package name (`probepkg`), and
`R_useDynamicSymbols(dll, FALSE)` (upstream sets this; it forbids the
usual dynamic-lookup fallback, so every entry point must be explicitly
registered).

Produced in Phase 0 (`catboost-8z4.2`). Findings recorded in
`docs/phase-0/catboost-8z4.2-report.md`.

## What it proves

1. `R_registerRoutines()` **replaces** a DLL's routine table on every
   call — it does not merge across calls. Calling it once from a
   hand-written `init.c` and again from cpp11's generated
   `R_init_<pkgname>` silently drops whichever table was registered
   first. The failure is silent: the package builds, installs, and
   loads; only the dropped entry point fails, at call time.
2. The fix: **one** combined `R_CallMethodDef` table containing both
   the raw `.Call` entry and cpp11's individual `extern "C"` wrapper
   symbol, registered by **one** `R_registerRoutines` call from the
   hand-written `init.c`. cpp11's own generated `R_init_probepkg` is
   never invoked — it is dead code here regardless, because its symbol
   name binds to the package name (`probepkg`) while the shared object
   is named `libprobe`, so `dyn.load()` would never auto-invoke it.
3. Both entry kinds stay reachable with
   `R_useDynamicSymbols(dll, FALSE)` retained, matching upstream.
4. `R CMD check` produces no registration-related NOTE or WARNING (the
   only WARNING/NOTEs present are unrelated administrative ones from
   this throwaway package's DESCRIPTION/documentation, not from the
   registration mechanism).

## Layout

- `probepkg/src/init.c` — hand-written. Defines the raw `.Call` entry
  `RawScalar_R` (returns `42L`), forward-declares cpp11's wrapper
  symbol `_probepkg_cpp11_scalar`, and is the **only** place
  `R_registerRoutines` is called (see the file's own comment for the
  attempt that failed and why).
- `probepkg/src/cpp11probe.cpp` — hand-written. One `[[cpp11::register]]`
  function, `cpp11_scalar()`, returning `99L`.
- `probepkg/src/cpp11.cpp`, `probepkg/R/cpp11.R` — **generated** by
  `cpp11::cpp_register()` from `cpp11probe.cpp`; committed so the
  package builds without re-running roxygen/cpp11 tooling. Do not
  hand-edit; regenerate with `cpp11::cpp_register()` if
  `cpp11probe.cpp`'s registered functions change.
- `probepkg/R/probepkg.R` — hand-written. `raw_probe()` calls
  `RawScalar_R` via `.Call(..., PACKAGE = "libprobe")` (the *shared
  object* name, not the package name — this is the naming mismatch
  the probe exists to exercise).
- `probepkg/NAMESPACE`, `probepkg/DESCRIPTION` — hand-written package
  metadata. `useDynLib(libprobe, .registration = TRUE)`.

Build artifacts (`*.o`, `*.so`, `probepkg.Rcheck/`, `*.tar.gz`) are not
committed; they are trivially regenerated by the build/run steps below.

## Build and run

From this directory:

```sh
R CMD build probepkg
R CMD INSTALL probepkg_0.0.1.tar.gz
Rscript -e '
  library(probepkg)
  cat("raw_probe():", raw_probe(), "\n")
  cat("cpp11_scalar():", cpp11_scalar(), "\n")
  cat("dynamicLookup:", getLoadedDLLs()[["libprobe"]][["dynamicLookup"]], "\n")
'
```

To reproduce the `R CMD check` result:

```sh
R CMD check probepkg_0.0.1.tar.gz
```

## Expected output

```
raw_probe(): 42
cpp11_scalar(): 99
dynamicLookup: FALSE
```

`R CMD check` status: 1 WARNING (undocumented objects — this probe ships
no `.Rd` files, irrelevant to the registration question), 2 NOTEs
(license-template boilerplate, an unused `Imports: cpp11` declaration
that `LinkingTo` alone already satisfies) — **zero** registration-related
NOTEs or WARNINGs.
